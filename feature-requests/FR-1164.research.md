## What the run did and did not establish

The run produced four rows, not four alternatives: three personas proposed
the same boundary check and the librarian restated the Anthropic stop-reason
guidance. All four were marked `pursue`. Two of its claims are wrong and are
corrected here, not carried as evidence:

- **"The provider factory already wraps all LangChain invoke calls" — false.**
  `create_llm` (`yamlgraph/utils/llm_factory.py`) builds and caches client
  objects and returns them; it never sees a response. The first yamlgraph
  code that holds a response is `attempt_structured_invoke`
  (`yamlgraph/executor_base.py:404-447`), `invoke_structured` /
  `ainvoke_structured` (`yamlgraph/utils/structured_output.py:100-147`) and
  `_invoke_candidate_async` (`yamlgraph/node_factory/race_node.py:118-186`).
- **"One check at `attempt_structured_invoke` entry catches all node types" —
  false.** The race node calls `ainvoke` itself (`race_node.py:173,180`) and
  agent finalisation binds directly; neither passes through it.
- **The data-process persona failed** schema validation (its
  `solution_class` was free text). Its idea, carrying stop reason and
  reasoning tokens downstream as schema fields, is dispositioned below as a
  rejected alternative; it is not a successful finding.
- The run tested no provider behaviour. The provider rows below come from
  the offline package reads and the live probe, not from the personas.

**Is this a graph?** No. It is a deterministic check on a provider response
at the point yamlgraph first holds it. No model judgement is involved; an
LLM graph would add cost and a failure mode to a field comparison.

Live probe, `claude-haiku-4-5-20251001`, `max_tokens=16`, 3 requests (about
$0.002; operator approval 2026-11-14: at most 4 requests, $0.05), producing
SHA `3fd52fec`:

- **Plain:** `stop_reason: "max_tokens"`, `output_tokens: 16`, content a
  plain string `"1. Afghanistan\n2. Albania\n3. Algeria\n4."`. Today
  `attempt_structured_invoke` returns that text as the answer.
- **Structured, `json_schema`, `include_raw=True`:** the envelope is
  `{raw, parsed, parsing_error}`. `raw.response_metadata.stop_reason` is
  `"max_tokens"`; the raw text is the cut JSON
  `{"countries":["Afghanistan",…,"Angola","`. **`parsing_error` is `None`
  and `parsed` is `Countries(countries=[…, 'Angola', ''])`**: the library's
  partial-JSON parser closes the cut string and array. No exception is
  raised.
- **Today's `invoke_structured`:** returns the same
  `Countries(countries=[…, 'Angola', ''])` as a success.
- `usage_metadata` carries no `output_token_details` on this non-thinking
  model, so the reasoning count is unavailable, not zero.

The structured finding changes the problem statement: a cut structured reply
is not "a parser error with an empty body"; it is a valid-looking model with
a fabricated trailing element. Only the raw message's stop reason exposes
it.
