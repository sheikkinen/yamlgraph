## Summary

Two of the three CLI backends of the copilot node accept exactly one vendor
release:

| Backend | Module | Pin | Installed here (2026-10-14) |
|---|---|---|---|
| `claude` | [copilot_runtime_claude.py](../yamlgraph/node_factory/copilot_runtime_claude.py) | `CLAUDE_SUPPORTED_VERSIONS = {"2.1.255"}` → banner `2.1.255 (Claude Code)` | `2.1.296 (Claude Code)` — **refused** |
| `opencode` | [copilot_runtime_opencode.py](../yamlgraph/node_factory/copilot_runtime_opencode.py) | `OPENCODE_SUPPORTED_BANNERS = {"1.18.31"}` | not installed on this host |
| `copilot` | [copilot_runtime.py](../yamlgraph/node_factory/copilot_runtime.py) | **none** — no `--version` probe exists | `GitHub Copilot CLI 1.0.97.` |

All three CLIs auto-update, so each pinned backend breaks on every vendor
release until someone captures new evidence and commits a one-string
change. Replace each exact-version allowlist with a full-string banner
**shape** check; keep every boundary that actually guards correctness and
spend. The Copilot backend is the control case: it has run unpinned through
every Copilot CLI release, and this FR makes the other two match it rather
than adding a pin there.

## Value Statement

Operators keep working `claude` and `opencode` backends across vendor
auto-updates that preserve the consumed contracts, without an allowlist-only
repo change per release — the property the `copilot` backend already has.

## Problem

### Claude Code

Witnessed 2026-10-14 on this host:

```
> claude --version
2.1.296 (Claude Code)
```

Pin at `copilot_runtime_claude.py:36`:
`CLAUDE_SUPPORTED_VERSIONS = frozenset({"2.1.255"})`. `_check_version`
raises `unsupported Claude Code version '2.1.296 (Claude Code)'` before the
auth probe, so every Claude node fails. The patch number moved by 41 since
the pin was captured; any auto-update in between broke the backend the same
way.

What the pin was meant to protect (FR-959 §3–§4), and what already guards it
without the pin:

| Risk the pin covered | Guard that already exists independently |
|---|---|
| Payer drift (API key / third-party billing) | `claude auth status` subscription check, every call (REQ-YG-641) + env stripping |
| `auth status` JSON shape change | `_ClaudeAuthStatus` Pydantic parse, fail-closed |
| Result envelope shape change | `_ClaudeEnvelope` strict parse, fail-closed (REQ-YG-639) |
| A flag disappears (e.g. undocumented `--max-turns`) | CLI non-zero exit → `RuntimeError` in `_parse_envelope` |
| Foreign binary named `claude` (PR #563 review P3) | **only** the banner product string — kept by this FR |

Every correctness contract that has a witness is enforced at the boundary
where the data enters (`the_one_law`). The version number added no guard of
its own for those contracts.

### Probe 1 — contracts on 2.1.296 (2026-10-14, read-only)

- `claude auth status` → keys
  `loggedIn,authMethod,apiProvider,analyticsDisabled,projectsDirectory,configDirectory,email,orgId,orgName,subscriptionType`;
  `loggedIn=True authMethod=claude.ai apiProvider=firstParty`. The three
  fields `_ClaudeAuthStatus` reads are present with the evidenced values.
- `claude --help` still lists `--tools`, `--allowedTools`, `--model`,
  `--output-format`, `--resume`, `-c/--continue`, `--add-dir`,
  `--dangerously-skip-permissions`. `--max-turns` is absent from `--help`,
  as it was on 2.1.255 (FR-959 evidence §4.3).

### opencode

Pin at `copilot_runtime_opencode.py:35`:
`OPENCODE_SUPPORTED_BANNERS = frozenset({"1.18.31"})`; same raise-before-run
shape as Claude. opencode's `--version` banner is a bare `X.Y.Z` with no
product string (FR-1048 evidence §1), so there is no foreign-binary guard
to keep — only the shape.

| Risk the pin covered | Guard that already exists independently |
|---|---|
| Event stream shape change | typed, fail-closed JSONL state machine: unknown `type`/`part.type`, reason outside `{stop, tool-calls}`, missing/duplicate terminal, session-ID drift all raise (REQ-YG-679) |
| Payer drift | none needed: provider keys **are** the payer; `--model` is a compile-time requirement (REQ-YG-681) — version-independent |
| A flag disappears (`--format`, `--model`, `--session`) | non-zero exit → `RuntimeError` |

### Copilot (control case)

`git grep -i version yamlgraph/node_factory/copilot_runtime.py` → no hits.
The `copilot` backend has never probed `copilot --version`; it has run
through every Copilot CLI auto-update up to `1.0.97` (this host) with the
judge and review adapters on it. That is the existence proof that an
unpinned CLI backend is operable here. No change to the Copilot runtime;
the FR adds a guard test so a pin is not introduced there by imitation.

## Ideal Result

A vendor CLI release that preserves the accepted banner shape, payer,
argv, and typed output contracts never requires an allowlist-only
YAMLGraph commit, for any copilot-node backend. A release that changes a
consumed contract still fails closed at the typed boundary and may need a
repo change — this FR does not promise otherwise. Each refusal names the
exit code and what was observed.

## Proposed Solution

In `copilot_runtime_claude.py`:

1. Delete `CLAUDE_SUPPORTED_VERSIONS` and `CLAUDE_SUPPORTED_BANNERS`.
2. Add `CLAUDE_BANNER_RE = re.compile(r"([0-9]+\.[0-9]+\.[0-9]+) \(Claude Code\)")`,
   applied with `fullmatch` to the stripped stdout.
3. `_check_version` keeps its position (before auth, every invocation, no
   cache) and returns the captured version for the existing `logger.info`
   line. It raises on non-zero exit or non-matching banner; the message
   names the exit code, the expected shape, and the observed stdout and
   stderr, each bounded to `_HEAD` characters.
4. Update `__all__` and the module docstring ("exact CLI version" →
   "Claude Code product banner").

In `copilot_runtime_opencode.py`:

1. Delete `OPENCODE_SUPPORTED_BANNERS`.
2. Add `OPENCODE_BANNER_RE = re.compile(r"[0-9]+\.[0-9]+\.[0-9]+")`, applied
   with `fullmatch` to the stripped stdout.
3. `_check_version` keeps its position and return value; same failure
   message contract as Claude.
4. Update `__all__` and the module docstring ("Exact-version preflight" →
   "Version-banner preflight"; drop "widening needs a new capture").

Copilot runtime: no code change.

## Alternatives Considered

Six solution classes. `is_this_a_graph`: **no** — this is a per-invocation
string check inside an existing runtime module; no item set, no LLM
judgement, no fan-out. `yamlgraph graph list` holds nothing that applies.

| # | Solution class | Precedent | Effort / risk | Disposition |
|---|---|---|---|---|
| 1 | **Widen the allowlist** per release with a new evidence capture | FR-959 §4 rule; FR-1048 copied it | Trivial per release / recurring outage between release and commit — the defect this FR names | Rejected |
| 2 | **Delete the version probe** entirely | Copilot backend (`copilot_runtime.py`) has none and works | Smallest diff / loses the PR #563 P3 foreign-binary guard (Claude) and the named missing-binary preflight (opencode) | Rejected for both; the probe is kept |
| 3 | **Minimum-version floor** (`>= 2.1.255`, `>= 1.18.31`) | Common in tool wrappers (`npm engines`) | One constant per backend / no witnessed defect on older releases motivates a threshold; a floor is a forecast | Rejected |
| 4 | **Banner shape check** (proposed) | FR-1146 normalized at the provider boundary rather than pinning models; `the_one_law` | Small / accepts a release whose flag semantics changed silently — see dissent | **Accepted** |
| 5 | **Capability probe** (`--help` grep for each mapped flag every call) | FR-959 evidence §4 was a one-off `--help` read | Medium, one extra subprocess per call / `--max-turns` is already absent from `--help` on the accepted release, so the probe would refuse a working CLI | Rejected |
| 6 | **Cache the probe result per process** | none; FR-959 judgement R-2 forbids it | Small / a cached pass outlives `claude logout`; orthogonal to pinning | Rejected |

**Preserved dissent (against #4).** The pin did one thing no typed boundary
does: it froze *flag semantics*. A future Claude release could keep
`--max-turns` parseable but change its meaning, or a future opencode could
change what `--model` resolves to, and neither non-zero exit nor envelope
parsing would notice. This FR accepts that risk on the evidence that the
Copilot backend has carried it unpinned without a recorded incident, and
because the pin converted *every* release into an outage to guard against
*some* release's semantic drift. The shape check does not predict semantic
drift; it is not claimed to.
