# Feature Request: CI Hardening Consolidation

**Priority:** HIGH
**Type:** Enhancement
**Status:** Proposed
**Effort:** 2 days
**Requested:** 2026-04-24

## Summary

Consolidate and harden CI/CD workflows with performance optimizations, security improvements, and better resource management.

## Value Statement

Development teams get faster, more reliable CI with reduced resource waste and improved security scanning for all tagged releases.

## Problem

Current CI workflows lack several hardening features that impact performance, reliability, and resource efficiency:

1. **Resource waste**: No concurrency control allows stale runs to consume unnecessary resources
2. **Slow builds**: Missing dependency caching increases build times
3. **Poor naming**: "Release to PyPI" is misleading for PR workflows  
4. **Race conditions**: Security scans fail on fresh tags due to PyPI indexing delays
5. **Limited coverage**: Only testing Python 3.12 when project supports 3.11+
6. **Missing validation**: Tag pushes don't validate version consistency

## Proposed Solution

Implement comprehensive CI hardening across all workflow files:

### 1. Concurrency Control
Add `concurrency` groups with `cancel-in-progress` to prevent resource waste:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

### 2. Dependency Caching
Enable pip caching in all `setup-python` steps:

```yaml
- name: Set up Python
  uses: actions/setup-python@v5
  with:
    python-version: '3.12'
    cache: pip
```

### 3. Workflow Naming
Rename "Release to PyPI" to "CI" to reflect its dual purpose (PR testing + releases).

### 4. Security Scan Resilience
Add retry logic around `pip-audit` for PyPI indexing race conditions:

```yaml
- name: Run pip-audit with retry
  uses: nick-fields/retry@v3
  with:
    timeout_minutes: 10
    max_attempts: 3
    retry_wait_seconds: 30
    command: pip-audit --strict --desc
```

### 5. Python Version Matrix
Test against both supported versions (3.11, 3.12):

```yaml
strategy:
  matrix:
    python-version: ['3.11', '3.12']
```

### 6. Release Validation
Add version consistency checks on tag pushes:

```yaml
- name: Validate tag version
  run: |
    VERSION="${GITHUB_REF#refs/tags/v}"
    PYPROJECT_VERSION=$(python -c "import tomllib; print(tomllib.load(open('pyproject.toml', 'rb'))['project']['version'])")
    if [ "$VERSION" != "$PYPROJECT_VERSION" ]; then
      echo "::error::Tag version ($VERSION) != pyproject.toml version ($PYPROJECT_VERSION)"
      exit 1
    fi
```

## Acceptance Criteria

- [ ] All workflows (workflow.yml, security.yml, commitlint.yml) have concurrency groups with cancel-in-progress
- [ ] All `setup-python` steps include `cache: pip`
- [ ] Main workflow renamed from "Release to PyPI" to "CI"
- [ ] Tag pushes validate version matches pyproject.toml
- [ ] pip-audit has retry mechanism (3 attempts, 30s intervals)
- [ ] Test matrix includes Python 3.11 and 3.12
- [ ] All existing jobs maintain their current dependencies and triggers
- [ ] Security scan still blocks on vulnerabilities found
- [ ] Release process remains unchanged (tag push → test → build → publish → release)

## Alternatives Considered

1. **Gradual rollout**: Implementing changes one workflow at a time
   - Rejected: Coordination overhead and inconsistent behavior
   
2. **External caching solutions**: Using ccache or similar
   - Rejected: pip cache is simpler and adequate for Python dependencies
   
3. **Different retry strategies**: Exponential backoff, different intervals
   - Current: Linear retry with 30s intervals sufficient for PyPI indexing

## Research Brief

### Competitive Landscape

**GitHub Actions native patterns** are the standard approach for CI hardening:
- **Concurrency control**: GitHub's official documentation recommends `concurrency` groups with `cancel-in-progress: true` as the canonical pattern for preventing resource waste
- **Dependency caching**: `actions/setup-python@v5` includes built-in `cache: pip` support specifically for this use case
- **Retry mechanisms**: `nick-fields/retry@v3` and similar actions are community-standard solutions for flaky external dependencies
- **Matrix builds**: Native GitHub Actions `strategy.matrix` for testing multiple Python versions is the established pattern

**Alternative approaches considered but rejected:**
- External CI systems (CircleCI, Jenkins): Would require complete workflow migration
- Docker-based caching solutions: Overkill for Python dependencies
- Custom retry scripts: Community actions are more reliable and maintained

**Conclusion**: GitHub Actions native features handle all requirements. No external systems needed.

### Existing Abstractions

**YAMLGraph CI architecture already established**:
- `.github/workflows/workflow.yml`: Main CI pipeline (testing + release)
- `.github/workflows/security.yml`: Dedicated security scanning (FR-187)
- `.github/workflows/commitlint.yml`: PR validation gates (FR-127, FR-149, FR-150)
- `pyproject.toml`: Version source of truth
- Branch protection rules: Established enforcement boundary pattern

**Current CI patterns in use**:
- 4 `setup-python` instances across workflows (all would gain caching)
- 0 `concurrency` groups (gap this FR addresses)
- Separate workflows by concern (security vs release vs validation)
- Multiple required status checks pattern already proven

### Diary Precedents

**Enforcement boundary patterns** (Knowledge Graph `the_one_law`):
- **FR-150 reflection**: "enforcement must happen at the merge boundary, not downstream" — CI gates are the correct enforcement point
- **FR-187 reflection**: `framework_costume` trap — separate workflows for separate concerns (security vs release)
- **FR-149 reflection**: `audit_as_ritual` pattern — CI enforcement closed gaps that manual processes couldn't

**Relevant traps identified**:
- `downstream_fix`: Adding more PR checks when the fix is at the boundary level
- `framework_costume`: Treating all CI as one workflow when triggers differ
- `audit_gate`: "Audit without blocking mechanism = post-mortem before incident"

### Usage Evidence

**Existing abstractions using related features**:
- CI workflows: 3 active workflows that would benefit from concurrency control
- Python setup steps: 4 instances that would gain pip caching
- Security scanning: 1 workflow that needs retry resilience
- Matrix builds: 0 current usage, but project supports 3.11+ (clear gap)

**Real-world use cases beyond the proposal**: 
- All future workflows would inherit concurrency control pattern
- Version validation pattern reusable for other tag-based automation
- Retry pattern applicable to other external API calls
