**Prior art:** FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md is the judged FR itself. FR-791 (+ judgement) is the v1 orchestrator this FR extends — its judgement deferred recon/browser-sniff integration to v2, which this FR is; not a duplicate, the planned re-entry. ## What is sound

The problem is real and precedented: FR-809 names the first consumer as the first v1 `not_found` that a human later rescues by GitHub recon or browser network traffic (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:8-12`), while the parent plan already describes recon as mining GitHub for candidate URLs/auth/schema evidence (`docs/adaptive-probing-plan.md:85-91`) and browser-sniff as the route for `api_found == false AND is_spa == true` (`docs/adaptive-probing-plan.md:113-119`).

The strategic classification is **contrib/example**, not a framework primitive: the proposal changes the existing example orchestrator surface (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:18-25`), and graph-runtime manifests are the documented composition pattern (`docs/adaptive-probing-plan.md:28-32`; `reference/graph-yaml.md:1458-1464`). The dependencies are no longer speculative: recon is Enforced with a graph manifest and live smoke evidence (`feature-requests/FR-787-api-discovery-recon-step.md:5`, `feature-requests/FR-787-api-discovery-recon-step.md:122-133`), browser-sniff is Enforced with deterministic data/CAPTCHA smokes (`feature-requests/FR-789-api-discovery-browser-sniff-step.md:5`, `feature-requests/FR-789-api-discovery-browser-sniff-step.md:116-126`), and the actual manifests exist (`examples/api-discovery/steps/recon.tool.yaml:4-12`; `examples/api-discovery/steps/browser_sniff.tool.yaml:4-13`).

The single-responsibility boundary is acceptable: although recon and browser-sniff address different failure classes, FR-809 is one orchestration concern — integrating the two step manifests deliberately excluded from FR-791 v1 (`feature-requests/FR-791-api-discovery-orchestrator.md:16-22`, `feature-requests/FR-791-api-discovery-orchestrator.md:81-91`) so the orchestrator exhausts its planned inventory before terminal synthesis (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:27-34`).

## Required revisions

### R-1: Make SPA routing depend on router-visible ground truth

Add FR-810 as a hard dependency and require the orchestrator to route browser-sniff from parsed page-analysis output, not from upstream candidate hints. The FR currently allows "candidate hints or a dedicated router-visible flag" and says it can ship with the candidate-hints workaround if FR-810 is not enforced (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:71-77`, `feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:100-102`). That contradicts AC-03's claim that browser-sniff is entered only on the SPA-without-API path (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:88`) because FR-810 documents that current edge expressions cannot address fields inside graph-tool `result` strings (`feature-requests/FR-810-router-visible-tool-call-outputs.md:21-29`, `feature-requests/FR-810-router-visible-tool-call-outputs.md:43-58`). Fold this as: FR-809 is blocked until FR-810 is Enforced, the page-analysis `tool_call` exposes a parsed state key such as `page_findings`, and the browser-sniff edge condition is exactly on `page_findings.is_spa == true` and `page_findings.api_found != true`. Do not authorize candidate-hints routing for this FR.

### R-2: Freeze the cross-step state handoff table

Add a concrete node/state handoff table covering `use_recon`, recon input, candidate generation, endpoint/page parsed outputs, browser-sniff URL selection, and sniffed endpoint handoff. The FR says recon is gated by `use_recon` or a cheap hypothesis-shape condition (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:66-70`) but AC-02 only tests the disabled path (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:87`), so the default enabled path is underspecified. It also says browser-sniff enters from page-analysis and its `api_calls` re-enter platform-confirm (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:71-77`), but the current page-analysis schema returns only `api_found`, `is_spa`, `platform_candidates`, and `api_urls` (`examples/api-discovery/steps/page-analysis/prompts/analyze.yaml:33-36`, `examples/api-discovery/steps/page-analysis/prompts/analyze.yaml:50-64`) and does not name which page URL should be loaded. Fold this as a table that states at minimum: `use_recon` is an optional boolean defaulting true; recon runs before `generate_candidates` only when true; `generate_candidates` receives `recon_result` and original inputs; endpoint-probe exposes parsed `probe_findings`; page-analysis receives the HTML/portal URL list and exposes parsed `page_findings`; browser-sniff receives a single deterministic `sniff_url` chosen from the page-analysis input/probe HTML pages; `sniff_findings.api_calls` become the candidate endpoint evidence for the next confirmation/synthesis step.

### R-3: Reconcile `needs_manual` and `manual_reason` with the terminal schema

Revise the terminal result schema and synthesize prompt so a browser-sniff `needs_manual` hint can be represented mechanically. FR-809 AC-04 requires a CAPTCHA/auth smoke to terminate `needs_manual` with `manual_reason` propagated into the result (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:89`), and the browser-sniff step does expose `verdict_hint` plus `manual_reason` (`feature-requests/FR-789-api-discovery-browser-sniff-step.md:41-45`; `examples/api-discovery/steps/browser-sniff/prompts/sniff.yaml:81-88`). The current orchestrator terminal schema has `verdict`, `profile`, `reason`, `steps_tried`, and `alternatives`, with `additionalProperties: false` (`examples/api-discovery/prompts/synthesize.yaml:75-138`), so `manual_reason` cannot currently be propagated. Fold this as either an explicit `manual_reason` field on the terminal verdict shape, required when `verdict == "needs_manual"`, or revise AC-04 to assert that `reason` carries the exact browser-sniff manual reason. Do not leave the final field name implicit.

### R-4: Replace fixture-smoke prose with exact deterministic assertions

Revise AC-03 and AC-04 to name the exact deterministic fixture pages, dynamic handler, command shape, and assertions. The cited FR-784 fixture is valid evidence: `index.html` triggers `/api/data`, `/analytics/collect`, `/api/item?token=...`, and `/api/search?...` (`tests/fixtures/fr784_spa/index.html:6-11`), `captcha.html` contains CAPTCHA markup and a data fetch (`tests/fixtures/fr784_spa/captcha.html:5-9`), and the committed `_SpaHandler` serves `/api/data`, `/api/item`, `/api/search`, `/analytics/collect`, `/api/secure`, and HTML fixture pages (`tests/unit/test_fr784_network_sniff.py:93-131`). The FR's current smoke text is directionally right but not yet mechanically checkable because it says "served with its dynamic handler" and "CAPTCHA/auth fixture smoke" without fixing the command and terminal assertions (`feature-requests/FR-809-api-discovery-orchestrator-v2-recon-browser-sniff.md:88-90`). Fold exact assertions for: the SPA fixture visits browser-sniff, `steps_tried` includes `browser-sniff`, sniffed `/api/data`, `/api/item`, and `/api/search` are present in the terminal evidence/profile, telemetry is absent from API evidence, the CAPTCHA fixture returns `verdict == "needs_manual"`, and the manual reason equals `captcha` (or the revised terminal field from R-3).
