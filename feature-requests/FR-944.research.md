## Barrier join (R-1 amendment, 2026-08-31)

Added per FR-944 judgement R-1: the barrier-join solution class was chosen by
the FR author and is NOT what the persona rows below prescribe (they prescribe
index threading through `map_edge`/`sorted_add`). This section records the
class on its own evidence.

- **solution_class:** barrier-join (compiler-boundary correction)
- **is_this_a_graph:** Yes — the defect and the probe are both graph-shaped;
  the probe below is a YAMLGraph graph run, no scripts or subagents.

**Current scheduling path** (`_compile_map_to_map`,
`yamlgraph/compile/edge_compiler.py` L221–224): the downstream map's `Send`
router is attached directly to the upstream map sub-node
(`_map_<map1>_sub → conditional(map2 fan-out)`), so the router fires once per
upstream branch on task-local state where the collected list has one element —
`enumerate` yields 0 in every branch.

**Candidate scheduling path:** `_map_<map1>_sub → static edge → synthetic
pass-through join → conditional(map2 fan-out)`. LangGraph's superstep barrier
makes the join run once after all upstream tasks fan in; the router then sees
the merged state and enumerates the full collected list.

**Bounded LLM-free direct runtime probe** (two chained python-tool maps over
3 items; the candidate path expressed with an explicit pass-through node —
the exact topology the fix generates):

```bash
yamlgraph graph run <probe>/graph.yaml --var seed='a,b,c' --full
# <probe> nodes: parse -> first_map -> join (python pass-through) -> second_map
```

Observed output, candidate path (one join invocation, merged state):

```
firsts:  [{_map_index: 0, value: A}, {_map_index: 1, value: B}, {_map_index: 2, value: C}]
seconds: [{_map_index: 0, echo: A, seen_state_map_index: 0},
          {_map_index: 1, echo: B, seen_state_map_index: 1},
          {_map_index: 2, echo: C, seen_state_map_index: 2}]
```

Observed output, current path (same graph minus the join node):

```
seconds: [{_map_index: 0, echo: A, seen_state_map_index: 0},
          {_map_index: 0, echo: B, seen_state_map_index: 0},
          {_map_index: 0, echo: C, seen_state_map_index: 0}]
```

Observed `_map_index` sequences: current `[0, 0, 0]`; candidate `[0, 1, 2]`.
The durable executable form of this probe is the committed RED/GREEN suite
`tests/unit/test_fr944_map_to_map_index.py` (per R-2/R-3); no ignored `tmp/`
path is authoritative.

**Why preferred over the persona alternatives:**

- *Index threading through `map_edge`/`sorted_add`* (os-infra-primitivist,
  data-process-planner, yamlgraph-native-planner rows): threads a corrected
  index through a router that is still firing at the wrong time — it leaves
  the per-branch scheduling intact, so the independent-list N×M duplication
  hazard (witnessed: 6 sends instead of 2) remains, and 1→N expansion has no
  coherent inherited index. The barrier fixes the scheduling defect itself;
  index correctness, ordering, and cardinality follow without touching
  `map_compiler.py` or `state_builder.py`.
- *Delete chained maps* (subtractionist): removes a working pipeline shape
  used by examples/demos/corpus_census and forces every user into manual
  pass-through nodes — which is exactly what the barrier join generates
  mechanically; deletion pays migration cost to arrive at the same topology.
- *Airflow-style index metadata propagation* (librarian): Airflow's
  guarantee — chained mapped tasks preserve index identity across expansion
  boundaries — is the requirement, but its XCom-lineage mechanism assumes a
  scheduler-owned metadata channel YAMLGraph does not have. The barrier join
  achieves the same guarantee with LangGraph's native superstep fan-in, no
  new metadata plumbing.
