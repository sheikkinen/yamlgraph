Where the record agrees: both pursue rows converge on the shape this FR
proposes — collect via `gh pr list` with a cap and a truncation flag, do the
join and assembly in code per FR-703/FR-704, keep the git-only path unbroken,
and distinguish an empty axis from an unreachable one (Commandment 6). The
os-permissions row adds the workflow-token requirement this FR adopts as
AC-14.

Where it disagrees, preserved: the **Subtractionist dissents outright** —
delete the axis, keep the recap git-only, and document the blindness as a
non-goal, on the grounds that network auth plus remote coupling plus cron
budget may cost more than the value. The FR rejects that dissent on FR-702's
own precedent (a rejection is a deliverable, already decided for this
artifact) but adopts its cost concern as three binding constraints: one
network call, no per-PR LLM call, and no network dependency in the bare-repo
test (AC-12). The **librarian dissents on mechanism**, proposing the GitHub
GraphQL/REST timeline-events API for review rounds and state transitions;
the FR rejects the timeline axis as unrequired by its ideal result and keeps
`gh pr list` metadata only. The os-permissions row's `--var github_token`
parameter is also rejected: FR-821's cron freezes the graph's arguments, so a
new required input breaks the scheduled consumer — the token is read from the
environment by `gh` instead.

`is_this_a_graph`: three of four rows answer yes and reach for a census or
discover/extract/reduce pipeline. The FR answers **the graph already exists**
— `examples/demos/recap/graph.yaml`, in scheduled production use — so this is
one node inside it, not a new pipeline. That is the record's main
disagreement with the FR, and it is deliberate: FR-894's corpus map-reduce
pattern and FR-962's census shape both spend one LLM call per unit, and the
gap here is mechanical metadata with no classification to make.
