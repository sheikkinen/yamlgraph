**Verdict:** APPROVED WITH REVISIONS — channel C is a coherent contrib/example and the spike validates its core platform premise, but authority activates only after R-1 through R-7 make the reviewed/deployed worker identical, contract the typed boundary, isolate checkout credentials, prove Windows process-tree ownership, and make lifecycle, publication, and evidence claims total.

## What is sound

**Scope and single responsibility:** the first consumer and event are concrete, v1 fixes one target repository and one serial worker, and the payload enum reuses the two existing launchers rather than inventing another agent protocol (`feature-requests/FR-949-issue-queue-delegation.md:8`, `feature-requests/FR-949-issue-queue-delegation.md:45-59`, `feature-requests/FR-949-issue-queue-delegation.md:81-86`). Collecting A-vs-C run evidence is coupled operational measurement; the FR correctly reserves channel retirement for a separate disposition FR (`feature-requests/FR-949-issue-queue-delegation.md:88-90`). No orthogonal concern requires a SPLIT.

**Research and strategic classification:** the committed spike is substantive rather than ceremonial: it records a 26-second happy path, exact timeout behavior, an empty cancelled-run capture, and a surviving grandchild PID that falsified the platform-kills-everything assumption (`feature-requests/spike-evidence-fr949-gha-runner.md:14-30`). The alternatives table preserves channel-A and channel-B dissent and answers why the queue is a process boundary rather than a graph (`feature-requests/FR-949-issue-queue-delegation.md:109-118`). CAP-101/104/105 are in fact retired (`capabilities/CAP-101-a2a-call-node.yaml:1-7`; `capabilities/CAP-104-a2a-server-reference-docs.yaml:1-7`; `capabilities/CAP-105-a2a-consumer-phase2.yaml:1-7`). **Contrib/example** is the correct classification: this is one operator, one repository, and one worker built from existing GitHub-Issue, skill, launcher, and runner primitives, not a framework primitive with three independent use cases (`.github/skills/judge-fr/doctrine.md:51-57`).

**Architecture alignment and feasibility:** GitHub-Issue label lifecycle and author allowlisting have implemented precedent (`feature-requests/FR-243-github-issues-remote-inbox.md:33-54`; `feature-requests/FR-251-harden-remote-inbox.md:29-49`). The spike proves trigger, claim comment, issue publication, close, retry-by-label, scoped step environment, and the platform timeout on macOS, while explicitly withholding SHA checkout and Windows claims (`feature-requests/spike-evidence-fr949-gha-runner.md:16-22`, `feature-requests/spike-evidence-fr949-gha-runner.md:46-52`). The payload contracts are real: judge requires a non-empty verdict artifact, and research performs a schema verification plus provenance write (`scripts/judge.sh:10-20`, `scripts/judge.sh:55-62`; `scripts/research.sh:11-29`, `scripts/research.sh:63-84`).

**Measurability and testability:** the FR separates offline seam tests from live judge, timeout, and Windows-service witnesses (`feature-requests/FR-949-issue-queue-delegation.md:94-107`). It also names a closed status vocabulary, byte-safe artifact reassembly, credential leak fixture, exact issue argv/body, and no-descendant timeout outcome (`feature-requests/FR-949-issue-queue-delegation.md:77-79`, `feature-requests/FR-949-issue-queue-delegation.md:95-105`). Those are directly testable once the workflow invokes the same typed helpers the unit tests exercise; that wiring matters because independently green components do not prove the composed path (`.github/copilot-instructions.md:80-81`).

The strongest case against authority is not that channel C lacks a consumer or that GitHub Actions failed the spike. It is that the current FR calls the comms-repo workflow the source of truth while reviewing only a copy, treats drift checking as an optional mode, validates an untrusted YAML request before checkout without naming executable parser code, proves only environment-variable scrubbing while a PAT-backed checkout shares the payload worktree, calls a Windows mechanism a POSIX process group, and publishes the terminal result before cleanup can change it (`feature-requests/FR-949-issue-queue-delegation.md:41-42`, `feature-requests/FR-949-issue-queue-delegation.md:47-71`, `feature-requests/FR-949-issue-queue-delegation.md:75-79`). These are boundary and composition defects; the revisions below contract the design rather than replace it.

## Required revisions

### R-1: Make the reviewed worker bundle the deployable source of truth

Replace the two-source wording with one canonical, reviewed worker bundle under `.github/skills/issue-delegate/`: `delegate.yml`, `models.py`, `worker.py`, `windows_job.ps1`, and `sync-worker.sh`. The comms repository contains a deployed mirror, not an independent source of truth. `sync-worker.sh` must copy the bundle to its frozen comms-repo paths and verify byte equality after deployment; it must never copy credentials.

Every submission, not only `submit.sh --check-worker`, must fail closed before issue creation when the comms workflow/helper hashes differ from the canonical bundle or the Windows runner is offline. The claim and terminal records must include target SHA, comms workflow commit SHA, canonical bundle hash, run ID, runner name, and UTC timestamps. Unit tests must invoke the same `models.py`/`worker.py` entrypoints called by `delegate.yml`; tests of duplicated shell snippets do not satisfy the composition contract. Record the deployed comms commit and bundle hash in the FR. Because this changes CI-like execution infrastructure in another repository, human review of the exact deployed diff is a GATE (`.github/copilot-instructions.md:74`, `.github/skills/judge-fr/doctrine.md:97-100`).

### R-2: Complete the typed request and control-side freshness boundary

Add Pydantic `DelegationRequest`, `DelegationResult`, and closed status/error models. The worker must parse exactly one fenced YAML mapping with duplicate-key detection and `extra="forbid"` before target-repository checkout. Freeze `schema_version=1`, `task=judge|research`, a lowercase 40-hex SHA, normalized payload, and `0 < max_reported_credits <= 60`; the worker-enforced maximum, not caller preference, is authoritative.

Freeze payload grammar mechanically: `judge` accepts only committed repo-relative `feature-requests/FR-*.md` other than `*.judgement.md`; `research` accepts only a committed regular `.md` brief that passes `scripts/research_preflight.py`; both reject absolute paths, `..`, backslashes, control characters, leading `-`, non-regular files, escaping symlinks, and absence at the requested SHA before launch. `submit.sh` must use the same normalizer and compare HEAD with a freshly fetched remote default branch, not a potentially stale local `origin/main`. Retain exact mocked `gh issue create` argv/body/label assertions. These models satisfy the repository's typed-boundary law (`.github/copilot-instructions.md:41-47`, `.github/copilot-instructions.md:190`).

### R-3: Isolate the checkout credential from the payload worktree

Expand credential isolation beyond `GH_TOKEN`/`GITHUB_TOKEN` absence. The target checkout must use the single-repository Contents-read PAT only in its checkout step, set `persist-credentials: false`, remove checkout-created auth headers/helpers before payload launch, and prove the payload worktree and process environment contain no PAT bytes, `http.*.extraheader`, credential helper, askpass binding, GitHub CLI auth, or other configured GitHub credential. The live probe must include `gh auth status` failure plus sanitized `git config --show-origin` evidence; an anonymous public fetch is not a credential-isolation witness.

Apply one redaction function at every workflow-log, step-summary, comment, tail, and artifact-publication boundary. A literal configured secret or credential-pattern match yields `TOKEN_LEAK_DETECTED`; no artifact body is posted. Keep transformed/encoded exfiltration as explicit residual risk rather than claiming impossibility. This folds the cited incident's actual lesson: credential-helper/config state and optional per-call redaction are both unsafe boundaries (`docs/diary/2026-09-01-incident-fr948-token-in-git-config.md:22-26`, `docs/diary/2026-09-01-incident-fr948-token-in-git-config.md:40-45`, `docs/diary/2026-09-01-incident-fr948-token-in-git-config.md:61-63`).

### R-4: Contract v1 to the Windows worker and own its full process tree

Delete the production macOS fallback and the claim that the workflow is OS-agnostic. The macOS runner remains spike evidence only. V1 targets the labeled Huutokauppakone Windows service runner, which is the stated first consumer and the only host whose survival counts (`feature-requests/FR-949-issue-queue-delegation.md:42`, `feature-requests/FR-949-issue-queue-delegation.md:106`).

Replace “process group” with a Windows Job Object launcher in `windows_job.ps1`: create a Job Object with kill-on-close, launch the directly owned payload process suspended, assign it to the job before resume, capture the root PID, and close/terminate the job in unconditional cleanup. Rename the platform-neutral status to `PROCESS_TREE_KILL_FAIL`. `TIMEOUT` is valid only when the root and every recorded descendant are absent; otherwise `PROCESS_TREE_KILL_FAIL` outranks it. Before any live payload, a service-account preflight must prove Git Bash can execute `scripts/judge.sh` and `scripts/research.sh`, Copilot CLI is authenticated for that account, required Python/project dependencies resolve, and the runner service survives restart. The Windows judge and timeout witnesses must run under that service account. The macOS spike explicitly says Windows behavior remains unwitnessed and records a surviving descendant (`feature-requests/spike-evidence-fr949-gha-runner.md:6`, `feature-requests/spike-evidence-fr949-gha-runner.md:24-30`).

### R-5: Make lifecycle, platform failure, cleanup, and publication total

Separate an authorization skip from an attempted delegation. A non-allowlisted author produces a read-only workflow-run audit and no issue mutation, claim, payload, or `DelegationStatus`; remove `UNTRUSTED_AUTHOR` from the run-result enum. Excluding `github-actions` and the worker service identity remains mandatory.

Truthfully bound GitHub-owned recovery. A runner loss or platform cancellation can leave an issue open with `claimed` and no typed terminal comment; the Actions run URL is the durable record, and recovery is a documented allowlisted operator re-label that creates a new run ID. Remove claims that every platform failure becomes an issue-level typed result. Do not reintroduce a poller, heartbeat, or custom claim-recovery state machine.

Reorder the workflow so payload termination, checkout removal, volatile credential cleanup, artifact verification, redaction, credit interpretation, and status precedence complete before terminal publication and label/close mutation. `CLEANUP_FAIL` therefore can affect the published result. Define `COMMENT_POST_FAIL` as observable in the Actions log/step summary when issue publication itself is unavailable; the issue remains open and must not carry `done`. For every status, define whether the payload ran, which fields may be absent, where the status is observable, the final labels/open-close state, and whether operator relabeling is valid. Every API-failure seam must have an offline witness; no silent success-shaped fallback is permitted (`.github/copilot-instructions.md:192`).

### R-6: Freeze the bounded output and artifact identity contract

Replace “all agent output” with the actual contract: success posts a typed run summary plus the verified final artifact; failure posts the typed summary plus a bounded, redacted stdout/stderr tail. Judge success requires the fresh non-empty `tmp/draft-judgement.md` verdict artifact (`scripts/judge.sh:59-60`); research success requires the fresh `tmp/draft-alternatives.md` passing the committed artifact verifier (`scripts/research.sh:67-69`). Missing, stale, malformed, or task-mismatched artifacts fail even when the launcher exits zero.

Define the tail byte limit, invalid-UTF-8 behavior, unterminated-line behavior, and incremental Windows capture mechanism. Artifact comments must be at most 60,000 UTF-8 bytes including headers, never split a code point, and carry `run <id>`, target SHA, workflow SHA, canonical bundle hash, artifact SHA-256, and `part i/N`; ordered reassembly must be byte-identical to the safe original. Terminal machine-readable fields must include queue, execution, and end-to-end durations, credits or a typed unparseable value, task class, and final status. This applies the repository's code-identity and substance-over-shape rules (`.github/copilot-instructions.md:162`; `feature-requests/FR-949-issue-queue-delegation.md:88-90`).

### R-7: Fold the exact scope, traceability, criteria, and estimate into the FR

Replace D-1 through D-8 and AC-1 through AC-14 with the frozen tables and criteria below. Allocate `CAP-258` and `REQ-YG-637`, which are unused after CAP-257/REQ-YG-636 (`ARCHITECTURE.md:573-575`, `ARCHITECTURE.md:3152`), and use that exact marker on every test. Re-estimate effort after including the canonical worker bundle, deterministic deployment check, Windows Job Object launcher, and Windows service witnesses; the current “one ~60-line workflow” comparison describes the spike, not the authorized implementation (`feature-requests/FR-949-issue-queue-delegation.md:31`; `feature-requests/spike-evidence-fr949-gha-runner.md:10-12`).
