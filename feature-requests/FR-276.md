# Feature Request: Prompt Caching & CAG Baseline for Watcher2 Pipeline

**Priority:** HIGH
**Type:** Enhancement
**Status:** Implemented
**Effort:** 5 days
**Requested:** 2026-04-24

## Summary

Implement Anthropic prompt caching in prompt YAML via cacheable system segments so watcher2 can reuse stable prompt prefixes across calls within a cycle.

## Value Statement

Watcher2 operators get approximately 3x cost reduction and faster cycle times by caching the stable 80% of context (Scripture, architecture, diary, codebase structure) that is re-read identically across calls.

## Problem

Each watcher2 cycle consumes ~100-200k tokens across 8 LLM steps. Analysis of context composition:

| Context segment              | Tokens  | Stability       | Currently |
|------------------------------|---------|-----------------|-----------|
| Scripture + instructions     | ~8k     | Very stable     | Re-sent every call |
| ARCHITECTURE.md + CLAUDE.md  | ~12k    | Stable          | Re-sent every call |
| Diary + existing FRs         | ~20-40k | Grows slowly    | Re-scanned every research step |
| Codebase conventions         | ~15k    | Stable per day  | Re-discovered every implement step |
| **Proposal-specific content**| **~5-10k** | **Unique**   | **Actual new work** |

The stable prefix (~80% of tokens) is re-processed from scratch every cycle. This is the exact pattern that Cache-Augmented Generation (CAG) addresses: pre-process stable context into a KV cache, then only process the delta per query.

Anthropic prompt caching already provides this at the API level — cached prefixes cost 90% less and have near-zero TTFT for the cached portion. But yamlgraph has no mechanism to mark prompt segments as cacheable.

## Proposed Solution

### Phase 1: Anthropic-only prompt caching hints in YAML

Add an additive prompt field for segmented system content. Keep existing `system: |` fully supported for backward compatibility.

```yaml
# prompts/plan.yaml
system_segments:
  - content: |
      {{ scripture }}
      {{ architecture }}
      {{ diary_index }}
    cache: true
  - content: |
      {{ proposal }}
    cache: false

# Legacy format remains valid (no caching)
system: |
  You are watcher2 plan node.
```

Execution semantics:
- If `system_segments` is absent, behavior is unchanged (uses existing `system` field).
- If `system_segments` is present, it takes precedence over `system` field.
- For Anthropic provider: map each segment into content blocks with `cache_control: {"type": "ephemeral"}` on segments where `cache: true`.
- For non-Anthropic providers: concatenate segments into one system string in declared order and ignore `cache` flags gracefully.
- Support both string and list format for `system` field to maintain backward compatibility.

Integration surface (required in scope):
- `yamlgraph/executor_base.py` message preparation (single source of truth)
- `yamlgraph/executor.py` sync execution path
- `yamlgraph/executor_async.py` async execution path
- `yamlgraph/utils/prompts.py` prompt schema validation

## Alternatives Considered

1. **Full RAG with vector DB** — Overkill. The corpus fits in context. The problem is redundant re-processing, not retrieval accuracy.
2. **LangGraph CachePolicy (FR-032)** — Already exists for node-level caching within a single run, but doesn't address cross-run context reuse or provider-native prompt caching.
3. **Manual prompt deduplication** — Fragile. Prompt content evolves; manual splitting doesn't scale across 8 pipeline steps.
4. **Google Context Caching API** — Deferred to follow-up FR because it requires explicit cache object lifecycle/TTL contracts different from Anthropic segment hints.
5. **OpenAI predicted outputs** — Deferred to follow-up FR because it optimizes completion generation and does not share Anthropic's cache-control contract.

## Technical Notes

- Anthropic prompt caching has a short TTL window. Watcher2 planning steps usually complete within this window, enabling reuse within a cycle.
- The enforcement session (copilot-2) starts a new LLM session, so it would get its own cache warm-up on first call, then reuse for subsequent steps.
- LLM instance caching and prompt caching are separate concerns: client cache keying remains unchanged while prompt cache hints are message-level.
- Implementation must verify that `langchain_anthropic.ChatAnthropic` supports content-block-level `cache_control` injection through message metadata or content block construction.

## Implementation Notes

### Core Changes Made

1. **Modified `prepare_messages()` in `yamlgraph/executor_base.py`**:
   - Added support for `system_segments` field alongside existing `system` field
   - Added conflict detection - raises ValueError when both `system` and `system_segments` are provided
   - Added `_build_system_message_from_segments()` helper function
   - For Anthropic provider: creates SystemMessage with `additional_kwargs.content` containing content blocks with `cache_control: {"type": "ephemeral"}` for cached segments
   - For non-Anthropic providers: flattens segments into single SystemMessage content string
   - Supports both scalar string and list format for `system` field (list format treated as segments)
   - Handles empty segments list by creating empty SystemMessage

2. **Added `prepare_messages_async()` in `yamlgraph/executor_async.py`**:
   - Wrapper around sync `prepare_messages()` for async context consistency
   - Ensures identical behavior across sync/async executor paths

3. **Variable substitution and template processing**:
   - Extended existing `format_prompt()` and `validate_variables()` to handle segment content
   - Both simple `{var}` and Jinja2 `{{ var }}` syntax work in segment content
   - All segment content included in template variable validation

## Research Brief

### Competitive Landscape

- **Anthropic prompt caching**: Native API-level caching with `cache_control: {"type": "ephemeral"}` on content blocks. Cached tokens cost 90% less and have near-zero TTFT. Supports 5-minute (standard) and 1-hour (2x cost) TTL. All active Claude models supported.
- **Google Context Caching**: Explicit caching API requiring cache object lifecycle management with custom TTL contracts. More complex than Anthropic's segment hints approach.
- **LangChain caching**: Traditional client-side caching focused on identical requests rather than prompt prefix caching. Does not support provider-native optimizations.
- **CrewAI**: No specialized prompt caching features identified - relies on underlying LangChain caching.
- **Pydantic AI**: Has compaction capabilities and capability-level optimizations, but no evidence of provider-native prompt segment caching.
- **OpenAI predicted outputs**: Optimizes completion generation, different from input prefix caching.

### Existing Abstractions

- **FR-032 (Node-Level Caching)**: Implemented LangGraph `CachePolicy` for caching node execution results within a single run. Addresses different problem (redundant computation) vs prompt-level caching (redundant token processing).
- **LLM instance caching**: `_llm_cache` in `yamlgraph/utils/llm_factory.py` caches LLM client instances by configuration tuple. Separate concern from message-level caching.
- **Prompt loading**: `yamlgraph/utils/prompts.py` loads and validates YAML prompts but no caching layer for parsed prompt configs (identified as gap in diary entries).
- **Message preparation**: `prepare_messages()` in `executor_base.py` is the single point where system/user messages are constructed - ideal integration point for segmented system content.

### Diary Precedents

- **2026-04-19 FR-032 reflection**: "When integrating framework-specific types (LangGraph CachePolicy), always translate at the compilation boundary. YAML config should express user intent; the compiler converts to framework objects." → Pattern established for provider-specific hints in YAML.
- **2026-04-19 philosopher corpus analysis**: "Prompt loading has no caching layer. If the same YAML prompt is referenced by 10 nodes, it's parsed 10 times." → Different problem (parse caching) but reinforces theme that caching gaps exist.
- **2026-04-12 research game engine**: "The only gap worth noting: prompt loading has no caching layer." → Recurring pattern identification.
