## First-party evidence (FR author, not persona output)

The librarian's cited URLs in both runs (`awesome-dsh-plugin.com`) could
not be independently confirmed and carry **zero evidentiary weight**.
They are retained above as provenance rather than deleted. The platform
contracts this FR relies on are instead taken from first-party
documentation, read 2026-09-08:

**macOS** — Apple, *Mac Automation Scripting Guide → Displaying
Notifications*
(<https://developer.apple.com/library/archive/documentation/LanguagesUtilities/Conceptual/MacAutomationScriptingGuide/DisplayNotifications.html>):

> To show a notification, provide the `display notification` command with
> a string to display. Optionally, provide values for the `with title`,
> `subtitle`, and `sound name` parameters […]

and, decisive for the submission-not-delivery semantics required by
judgement R-2:

> Notifications are shown as alerts or banners, depending on the user's
> settings in System Preferences > Notifications.

> After using a script to display a notification, the script or Script
> Editor […] is added to the list of notifying apps in System
> Preferences > Notifications.

Apple therefore documents presentation as *user-settings dependent* and
the calling process as a registrable notifying app whose notifications
can be configured — i.e. a successful `osascript` exit proves submission,
never display.

**Windows** — Microsoft Learn, *ToastNotificationManager Class*
(<https://learn.microsoft.com/en-us/uwp/api/windows.ui.notifications.toastnotificationmanager>):

> Creates `ToastNotifier` objects that you use to raise toast
> notifications. This class also provides access to the XML content of
> the system-provided toast templates […]

> **Sending toast notifications from desktop apps** […] For a desktop app
> to display a toast, the app must have a shortcut on the Start screen.
> The shortcut must have an `AppUserModelID`.

> Device family: Windows 10 (introduced in 10.0.10240.0)

This is the AUMID constraint the FR freezes: a desktop process cannot
raise a toast anonymously, it must present the identity of a
Start-menu-shortcutted app. `CreateToastNotifier(String)` is the
documented overload that accepts that identity. The example in the same
page shows the required content path — `GetTemplateContent(...)`,
`GetElementsByTagName("text")`, `CreateTextNode(...)`,
`new ToastNotification(xml)`, `.Show(toast)` — which is exactly the
sequence the frozen PowerShell script performs.

**Linux** — freedesktop.org, *Desktop Notifications Specification*,
version 1.3, 18 August 2024
(<https://specifications.freedesktop.org/notification-spec/latest/>):

> This is a standard for a desktop notifications service, through which
> applications can generate passive popups to notify the user in an
> asynchronous manner of events.

> This specification explicitly does not include other types of
> notification presentation such as **modal message boxes**, window
> manager decorations or window list annotations.

Two consequences are load-bearing. First, the spec defines a
*service* an application talks to: if no notification daemon owns
`org.freedesktop.Notifications`, there is nothing to submit to — hence
the FR's explicit Linux prerequisite. Second, the spec's exclusion of
modal message boxes is the reason the `yamlgraph-native-planner`
persona's `win32api.MessageBox`/`ctypes` suggestion is rejected in the
FR: a modal dialog is definitionally not a notification, it steals focus
and blocks, which inverts the requirement.
