## What the raw records say

1. **The cache works on both 5.5 models through the existing `system_segments` path.** The first call writes
   2,927 tokens and every later call reads them. FR-1055's fix holds on the new models.
2. **A surprise in LangChain's normalisation.** When Anthropic sends the per-TTL breakdown, `langchain-anthropic`
   1.7.0 sets `input_token_details.cache_creation` to **0** and puts the written tokens in
   `ephemeral_5m_input_tokens` or `ephemeral_1h_input_tokens` instead. The raw API field
   `cache_creation_input_tokens` is 2927. A meter that summed `cache_creation` would report that nothing was ever
   written. The write count is `ephemeral_5m + ephemeral_1h`, or `cache_creation` when there is no breakdown.
3. **`input_tokens` counts all prompt tokens, cached or not.** The raw `input_tokens` is 11, which is only the
   uncached tail. LangChain's `input_tokens` is 2938, which is 11 + 2927, whether the 2927 tokens were written or
   read. `--token-usage` therefore prints the same 2938 for a write and for a read. A read is billed at 0.1× on
   Haiku 5.5 and 0.05× on Sonnet 5.5, so the printed number cannot be priced.
4. **Below the minimum, nothing happens and no error is raised (case B).** With 328 tokens, `cache_control` is
   accepted and does nothing. No write, no read and no warning are reported.
5. **A breakpoint on a varying segment costs extra and never reads (case C).** Every call writes, at 1.25× the
   input price, and no call reads. This matches the documentation's "common mistake".
6. **Automatic caching is the wrong tool for single-shot nodes (case F).** The top-level kwarg goes through
   LangChain unchanged and is accepted. But the breakpoint lands on the last block, which is the varying user
   message, so it behaves like case C: it writes every time and never reads.
7. **Both 1-hour TTL (D) and a user-message breakpoint (E) work through LangChain** when the block is built by hand,
   with no beta header. yamlgraph cannot express either one yet. Both stay deferred until a consumer needs them.
8. **Latency** dropped on the read calls for Haiku (1.44 s to 0.73 s), but at this prefix size the difference is
   within noise. It is not a finding.
9. **Unrelated observation:** Haiku 5.5 thinks by default. All 32 output tokens went to `reasoning`. This was
   already handled by FR-1148 and FR-1152 and is noted only so that a reader of the raw records is not surprised.

## Map fan-out spike (run_id `2a47aea8`)

- **Script:** `tmp/spike_prompt_cache/spike_map.py` (not committed).
- **What it imitates:** a `type: map` LLM node. Every branch gets the same cached `system_segments` block of
  2,841 tokens and its own one-line user message.
- **Setup:** N = 12 items, dispatched with `ainvoke` under a semaphore of width W.
  - W = 8 is yamlgraph's `DEFAULT_MAX_CONCURRENCY` (`utils/validators.py`).
  - **The run did not go through a real map node.** LangGraph's map dispatch, `Send` plus `max_concurrency`, has
    the same concurrency limit, but this still needs a check through an actual graph.
- **Cost column:** input cost in base-price token units, with writes at 1.25× and reads at 0.1× on Haiku or 0.05×
  on Sonnet.

| Model | Variant | Writes | Reads | Input cost vs uncached | Wall |
|---|---|---|---|---|---|
| Haiku 5.5 | `seq` (W = 1) | 1 | 11 | 0.199 | 11.6 s |
| Haiku 5.5 | `par8` (W = 8, cold) | **8** | 4 | **0.867** | 2.6 s |
| Haiku 5.5 | `warm8` (1 call, then W = 8) | 1 | 11 | 0.199 | 3.4 s |
| Sonnet 5.5 | `seq` | 1 | 11 | 0.154 | 16.6 s |
| Sonnet 5.5 | `par8` | **8** | 4 | **0.851** | 2.9 s |
| Sonnet 5.5 | `warm8` | 1 | 11 | 0.154 | 4.6 s |

### What the map records say

1. **Parallel branches do not share a cache entry that is still being written.** Items 1 to 8 started together and
   each one paid a full 1.25× write. Only items 9 to 12, which started after the first wave had answered, read from
   the cache. The cache is only available once a response exists, and the spike shows this directly.
2. **On a cold cache, a parallel map makes about W writes and N − W reads.** When the shared prefix dominates the
   prompt, the input cost compared with no caching is

   $$\frac{1.25\,\min(W,N) + r\,\max(N-W,0)}{N}$$

   where $r$ is the read multiplier. Caching is cheaper than no caching only when

   $$N > W\,\frac{1.25-r}{1-r}$$

   With W = 8 that is **N > 10.2 on Haiku 5.5** and **N > 10.1 on Sonnet 5.5**.
   - **For maps of 10 items or fewer at the default width, caching costs more than not caching.** At N ≤ 8 every
     branch writes, so the cost is 1.25× the uncached cost.
   - The saving only gets close to the sequential case for large N. Game-engine's library describe map runs
     9 to 140 calls. Without warming, the cost is about 1.12× at N = 9 (a loss) and about 0.17× at N = 140 (Haiku).
3. **"Warm first, then fan out" recovers the full saving.** One call goes out first, then the rest fan out. The
   result is 1 write and N − 1 reads, the same as running in sequence, at a cost of about one call's latency
   (0.7 to 1.8 s). Fully sequential runs were 3.5 to 4.5 times slower here.
4. **This changes the earlier recommendation.**
   - R5 in the research doc listed warm-first as deferred, waiting for a consumer whose first wave is measured to
     cost more than a cent.
   - For any map with a cached segment and N ≤ about 10 at the default width, caching is a **net loss** unless the
     map warms first.
   - So a map node that inherits `cache: true` segments should either warm first or at least get a lint warning.
     That decision belongs in its own FR. It still needs FR-1155's meters first, so the effect can be seen in real
     runs.
5. **The meter trap reproduced.** Every write appeared in `ephemeral_5m_input_tokens`, with `cache_creation` = 0.
