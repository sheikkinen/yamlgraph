# Feature Request: Anthropic Prompt Caching Demo with System Segments

**Priority:** MEDIUM
**Type:** Feature
**Status:** Implemented
**Effort:** 2 days
**Requested:** 2026-04-25

## Summary

Create a practical demonstration of Anthropic prompt caching using system_segments to validate FR-276's implementation and provide a working example for graph authors.

## Value Statement

Graph authors get a concrete working example of how to leverage Anthropic prompt caching with system_segments, enabling them to optimize costs and performance in their own multi-step workflows by caching stable context.

## Problem

FR-276 implemented system_segments with cache: true support for Anthropic prompt caching, but there is no practical demonstration showing how to use this feature effectively. The existing cache demo (examples/demos/cache/) focuses on node-level result caching (FR-032), not prompt-level token caching.

Without a working demo, graph authors cannot:
- Understand how to structure prompts with cacheable segments
- See the cost/performance benefits in practice
- Learn best practices for segment design
- Validate that their cache hints are working correctly

## Proposed Solution

Create `examples/demos/prompt-caching/` with:

1. **Two-node graph** using provider: anthropic with shared cached system context
2. **Shared prompt template segments** demonstrating cache reuse across nodes
3. **Documentation** showing cache hit patterns and cost savings
4. **Working demo-output.log** proving execution with Anthropic API

### Graph Structure

```yaml
# examples/demos/prompt-caching/graph.yaml
version: "1.0"
name: prompt-caching-demo
description: Demonstrates Anthropic prompt caching with system_segments

provider: anthropic
prompts_relative: true
prompts_dir: prompts

state:
  topic: str

nodes:
  analyze:
    type: llm
    prompt: analyze
    variables:
      topic: "{state.topic}"
    state_key: analysis
    
  reflect:
    type: llm 
    prompt: reflect
    variables:
      topic: "{state.topic}"
      analysis: "{state.analysis}"
    state_key: reflection

edges:
  - from: START
    to: analyze
  - from: analyze  
    to: reflect
  - from: reflect
    to: END
```

## Research Brief

### Competitive Landscape

- **Anthropic prompt caching**: Native API-level caching with `cache_control: {"type": "ephemeral"}` on content blocks. Cached tokens cost 90% less (0.1x base price) with 5-minute TTL or 1-hour TTL (2x cost). All active Claude models supported. Two modes: automatic caching (system applies breakpoint) and explicit cache breakpoints (manual content block control).

- **LangChain caching**: Traditional client-side caching focused on identical requests rather than prompt prefix caching. Uses in-memory, SQLite, or Redis backends for response caching. Does not support provider-native optimizations like Anthropic's segment hints or Google's context caching.

- **CrewAI**: No specialized prompt caching features identified in documentation. Relies on underlying LangChain caching infrastructure for basic request deduplication.

- **Google Context Caching**: Explicit caching API requiring cache object lifecycle management with custom TTL contracts. More complex than Anthropic's segment hints approach, requiring separate cache create/delete operations.

- **OpenAI**: No equivalent prompt prefix caching. Has "predicted outputs" feature for completion optimization but addresses different use case (output generation vs input processing).

### Existing Abstractions

- **FR-032 (Node-Level Caching)**: `examples/demos/cache/` demonstrates LangGraph `CachePolicy` for caching node execution results within a single run. Uses `cache: true` or `cache: {ttl: 60}` syntax. Different problem domain (redundant computation) vs prompt-level caching (redundant token processing).

- **FR-276 (System Segments)**: Already implemented `system_segments` with `cache: true` support in `yamlgraph/executor_base.py`. Tests in `tests/unit/test_prompt_caching_fr276.py` verify Anthropic cache_control injection and non-Anthropic flattening behavior.

- **LLM Factory Pattern**: `yamlgraph/utils/llm_factory.py` provides `create_llm()` for multi-provider abstraction. Already handles Anthropic provider instantiation with proper client caching.

- **Prompt Loading**: 213 YAML files use `system:` field across codebase. All prompt files in `prompts/` directories would benefit from understanding cache optimization patterns.

### Diary Precedents

- **2026-04-24 FR-276 reflection**: "Provider-specific message formatting is more complex than anticipated. Anthropic's content block structure with `additional_kwargs.content` differs significantly from standard LangChain message patterns." → Pattern established for provider-specific optimizations requiring conditional logic.

- **2026-04-19 FR-032 reflection**: "When integrating framework-specific types (LangGraph CachePolicy), always translate at the compilation boundary. YAML config should express user intent; the compiler converts to framework objects." → Confirmed pattern for provider hints in YAML.

- **Recurring theme**: "Prompt loading has no caching layer. If the same YAML prompt is referenced by 10 nodes, it's parsed 10 times." → Different problem (parse caching) but reinforces that caching gaps exist at multiple levels.

### Usage Evidence

- Existing graphs using related abstractions: 1 (only `examples/demos/cache/` uses node-level caching)
- Total YAML files with `system:` prompts: 213 (extensive usage base for prompt caching education)  
- Files mentioning Anthropic provider: 30 (significant user base for provider-specific features)
- Real-world use cases beyond the proposal: Any long-context workflow with stable prefixes would benefit (research agents, document analysis, code review). Watcher2 is primary heavy-context user but pattern applies broadly to multi-step LLM workflows.
