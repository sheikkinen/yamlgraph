# FR-642: novel_fandom — Wiki Core Types (Premise + Synopsis)

**Priority:** MEDIUM
**Type:** Feature (example)
**Status:** Implemented
**Effort:** 0.5 days
**Requested:** 2026-07-01
**Depends on:** FR-637, FR-638, FR-639, FR-640

## Summary

Add `Premise` and `Synopsis` page types to the novel_fandom canon schema so
the generative provenance chain — from thematic seed to full wiki — is tracked
inside the canon itself. Every downstream page traces back to the premise
through `references`, enforced by the existing `ref_gate`.

## Value Statement

The bootstrap pipeline (Phase 2) needs a typed origin: the premise that seeds
generation and the synopsis that expands it. Without these types, the bootstrap
must inject untyped state or store provenance outside the canon. With them, the
canon is self-describing: a `Premise` page exists, a `Synopsis` page references
it, and every extracted character/faction/location/rule/event references the
synopsis. The existing gate validates the entire provenance tree for free.

## Problem

1. **No typed origin.** The current 8-page canon has characters, events,
   factions, locations, and rules — but no record of *why* they exist. The
   premise ("a world scarred by the Ashfall") lives in the author's head.

2. **No synopsis.** The dungeon_master example proved that a reveal-all
   synopsis is the essential intermediate step between premise and entities.
   It's the document from which the LLM extracts a manifest of entities to
   generate. Without it in the canon, the bootstrap pipeline has no
   persistent context to feed per-entity generation.

3. **No provenance chain.** When the wiki linter (Phase 3) checks for
   unreferenced pages or relationship symmetry, it needs to know what
   references what. If the synopsis isn't a page, extracted entities can't
   reference it, and the provenance tree has a gap.

## Design

### Premise page type

```python
class Premise(BaseModel):
    type: Literal["premise"] = "premise"
    id: str
    lane: Literal["static", "dynamic"]
    text: str  # The thematic seed — 1-3 paragraphs
    genre_tags: list[str] = Field(default_factory=list)
    era: str = ""
    themes: list[str] = Field(default_factory=list)
    references: list[str] = Field(default_factory=list)
```

Typically one per canon, `lane: static`. The text is the human-authored seed.

### Synopsis page type

```python
class Synopsis(BaseModel):
    type: Literal["synopsis"] = "synopsis"
    id: str
    lane: Literal["static", "dynamic"]
    text: str  # Full-disclosure reveal-all prose (DM-style)
    references: list[str] = Field(default_factory=list)
```

Generated by LLM from the premise. `lane: dynamic` initially, frozen to
`static` after human review (manual freeze). The `references` list must
include the premise id.

### Integration

- Add both to `PAGE_MODELS` dict and `validate_page()` dispatcher.
- No new graphs — these types are consumed by the bootstrap pipeline (Phase 2).
- Seed canon gets two new files: `premise.yaml` (the Ashfall thematic seed)
  and `synopsis.yaml` (a hand-written synopsis exercising the type).

### Provenance tree after this FR

```
premise (lane: static)
  └→ synopsis (lane: dynamic, references: [premise])
       ├→ character ×N (references include synopsis)
       ├→ faction ×M
       ├→ location ×K
       ├→ rule ×J
       └→ event ×E
```

Existing seed pages (kaelen, maren, voss, etc.) do NOT need to reference
the synopsis — they predate it. Only pages created by the bootstrap pipeline
will carry the synopsis reference. This is consistent: static seed pages
have no LLM provenance to trace.

## Judgement

**Verdict: APPROVED — scope is minimal, clear, and well-founded.**

### What's right

1. **Correct layering.** Premise and Synopsis are the two missing roots of the
   provenance tree. Adding them as typed canon pages — not special-cased state —
   means the existing `ref_gate` enforces provenance for free. No new gate code.

2. **Proven pattern.** The DM pipeline already validated that a reveal-all
   synopsis is the essential intermediate between seed and extracted entities.
   This FR ports the pattern into the wiki's typed model rather than inventing
   a new abstraction.

3. **Dependencies satisfied.** FR-637 (schema + seed) and FR-640 (enriched
   world model) are both Implemented. The foundation is solid.

4. **Tight scope.** Two Pydantic models, two seed YAML files, registration in
   `PAGE_MODELS`, tests. No graphs, no pipeline, no governance workflow. The
   scope exclusions are explicit and correct — bootstrap (Phase 2), wiki linter
   (Phase 3), and chapter outlines are properly deferred.

5. **Backward-compatible addition.** Existing 8 seed pages are untouched.
   Existing tests (57+) must continue to pass. New types are additive — the
   `validate_page()` dispatcher already handles unknown types with `ValueError`.

### Required corrections

1. **Add `Depends on: FR-638, FR-639` to the header.** The FR text says
   "57 tests from FR-637/640/638/639" must pass, implying a dependency on all
   four. The header only lists FR-637 and FR-640. Add FR-638 and FR-639 to be
   honest about the dependency graph — even though they're already Implemented,
   the acceptance criteria reference their test counts.

2. **Specify the CAP and REQ ID.** Acceptance criterion §7 says
   `@pytest.mark.req()` but doesn't name the requirement ID. Before enforcement,
   create a `CAP-XXX-novel-fandom-core-types.yaml` with the `REQ-YG-XXX` ID
   and reference it in the tests. Follow the pattern of existing CAPs.

3. **Synopsis `version` field is premature.** The FR explicitly excludes
   iterative rewriting ("No iterative synopsis rewriting — single version in
   seed"). The `version: int = 1` field implies a future iteration mechanism
   that doesn't exist and isn't tested. Remove it — add it in the FR that
   introduces iterative rewriting. YAGNI.

### Deferred considerations (accepted)

- Bootstrap pipeline (Phase 2) — correct to defer, the types must exist first.
- ChapterOutline type — correct to defer, Events + pathfinder suffice for now.
- Freeze governance — correct to defer, no lane-flip mechanism exists yet.
