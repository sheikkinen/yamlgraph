# FR-276: Prompt Caching & CAG Baseline (Phase 1)

# Feature Request: Prompt Caching & CAG Baseline for Watcher2 Pipeline

**Priority:** HIGH
**Type:** Enhancement
**Status:** Judged - Conditionally Approved (Phase 1 only)
**Effort:** 5 days
**Requested:** 2026-04-24
**Judged:** 2026-04-24

## Summary

Implement Anthropic prompt caching in prompt YAML via cacheable system segments so watcher2 can reuse stable prompt prefixes across calls within a cycle.

## Value Statement

Watcher2 operators get approximately 3x cost reduction and faster cycle times by caching the stable 80% of context (Scripture, architecture, diary, codebase structure) that is re-read identically across calls.

## Problem

Each watcher2 cycle consumes ~100-200k tokens across 8 LLM steps. Analysis of context composition:

| Context segment              | Tokens  | Stability       | Currently |
|------------------------------|---------|-----------------|-----------|
| Scripture + instructions     | ~8k     | Very stable     | Re-sent every call |
| ARCHITECTURE.md + CLAUDE.md  | ~12k    | Stable          | Re-sent every call |
| Diary + existing FRs         | ~20-40k | Grows slowly    | Re-scanned every research step |
| Codebase conventions         | ~15k    | Stable per day  | Re-discovered every implement step |
| **Proposal-specific content**| **~5-10k** | **Unique**   | **Actual new work** |

The stable prefix (~80% of tokens) is re-processed from scratch every cycle. This is the exact pattern that Cache-Augmented Generation (CAG) addresses: pre-process stable context into a KV cache, then only process the delta per query.

Anthropic prompt caching already provides this at the API level — cached prefixes cost 90% less and have near-zero TTFT for the cached portion. But yamlgraph has no mechanism to mark prompt segments as cacheable.

## Proposed Solution

### Phase 1: Anthropic-only prompt caching hints in YAML

Add an additive prompt field for segmented system content. Keep existing `system: |` fully supported.

```yaml
# prompts/plan.yaml
system: |
  You are watcher2 plan node.

system_segments:
  - content: |
      {{ scripture }}
      {{ architecture }}
      {{ diary_index }}
    cache: true
  - content: |
      {{ proposal }}
    cache: false
```

Execution semantics:
- If `system_segments` is absent, behavior is unchanged.
- If `system_segments` is present and provider is Anthropic, map each segment into Anthropic system content blocks and set `cache_control: {"type": "ephemeral"}` only on segments with `cache: true`.
- If `system_segments` is present and provider is non-Anthropic, concatenate segments into one system string in declared order and ignore `cache` flags.

Integration surface (required in scope):
- `yamlgraph/executor_base.py` message preparation (single source of truth)
- `yamlgraph/executor.py` sync execution path
- `yamlgraph/executor_async.py` async execution path
- `yamlgraph/executor_async.py` streaming execution path

### Deferred Follow-up (Not in this FR)

- Baseline checkpointing via `--import-state` / `--export-state` (FR-269) will be handled in a separate FR after Phase 1 metrics are validated.
- Domain-clustered context selection is explicitly deferred to a future FR.

## Acceptance Criteria

- [ ] Existing prompts with scalar `system: |` remain valid with no behavior change.
- [ ] Prompt schema supports additive `system_segments` with per-segment `cache` boolean.
- [ ] Anthropic requests include `cache_control: {"type": "ephemeral"}` only on segments where `cache: true`.
- [ ] Non-Anthropic providers ignore cache hints and execute without errors by flattening `system_segments` to a single system string.
- [ ] Sync, async, and streaming executor paths share the same segment handling behavior.
- [ ] Unit tests cover Anthropic cache-control injection, non-Anthropic flattening behavior, and string/list coercion behavior.
- [ ] Performance gate: across at least 20 watcher2 runs on the same stable corpus, median prompt input tokens for plan+research+judge steps is reduced by >=40% vs uncached baseline.
- [ ] `reference/prompt-yaml.md` documents `system_segments` and provider behavior.
- [ ] Requirement traceability is updated (`ARCHITECTURE.md`, `scripts/req_coverage.py`, and req-marked tests).

## Alternatives Considered

1. **Full RAG with vector DB** — Overkill. The corpus fits in context. The problem is redundant re-processing, not retrieval accuracy.
2. **LangGraph CachePolicy (FR-032)** — Already exists for node-level caching within a single run, but doesn't address cross-run context reuse or provider-native prompt caching.
3. **Manual prompt deduplication** — Fragile. Prompt content evolves; manual splitting doesn't scale across 8 pipeline steps.
4. **Google Context Caching API** — Deferred to follow-up FR because it requires explicit cache object lifecycle/TTL contracts different from Anthropic segment hints.
5. **OpenAI predicted outputs** — Deferred to follow-up FR because it optimizes completion generation and does not share Anthropic's cache-control contract.

## Technical Notes

- Anthropic prompt caching has a short TTL window. Watcher2 planning steps usually complete within this window, enabling reuse within a cycle.
- The enforcement session (copilot-2) starts a new LLM session, so it would get its own cache warm-up on first call, then reuse for subsequent steps.
- LLM instance caching and prompt caching are separate concerns: client cache keying remains unchanged while prompt cache hints are message-level.

## Judgement

**Verdict: Conditionally Approved — Phase 1 only. Phase 2 deferred. Phase 3 dropped.**

### What is right

The problem is real and well-quantified. Watcher2 re-sends ~80% identical context on every LLM call, across 7 calls per cycle. Anthropic's prompt caching directly addresses this — same-prefix content costs 90% less and has near-zero TTFT for the cached portion. The FR correctly identifies that the caching gap exists between FR-032 (node-level, single-run) and `_llm_cache` (client instances), neither of which address cross-call message-level caching.

FR-269 (`--import-state`/`--export-state`) is already implemented, so Phase 2 has no infrastructure blockers.

### Issues requiring correction before enforcement

#### 1. Cost reduction claim is inflated

The FR claims "5-10x cost reduction." The math doesn't support this. If 80% of tokens are cached at 10% cost: `0.8 × 0.1 + 0.2 × 1.0 = 0.28`, yielding **~3.5x** reduction. That's still significant — don't inflate it. Correct the Value Statement to "~3x cost reduction."

#### 2. `system: list` is a breaking schema change — needs migration path

The proposed syntax changes `system` from a string to a list of `{content, cache}` dicts. Every existing prompt YAML uses `system: "string"`. The FR must:
- Accept both forms: `system: str` (legacy, no caching) and `system: list[{content: str, cache?: bool}]`
- Parse the string form as a single uncached segment internally
- Add this as an explicit acceptance criterion

#### 3. Provider-specific hint leaks into declarative YAML

`cache: true` only works on Anthropic today. This is acceptable as a *hint* (the FR correctly says "ignore gracefully on other providers"), but the naming should be provider-neutral. The field name `cache: true` is fine — it's a general-purpose hint, not `anthropic_cache_control: true`. Keep it. But add a test that verifies graceful no-op on a non-Anthropic provider, and document in `reference/prompt-yaml.md` which providers honor it.

#### 4. LangChain message-level `cache_control` injection mechanism

Anthropic's API expects `cache_control` on **content blocks**, not message-level metadata. The FR hand-waves the injection: "translate `cache: true` segments into `cache_control: {"type": "ephemeral"}`." The implementation must verify that `langchain_anthropic.ChatAnthropic` supports content-block-level `cache_control` injection — either through `additional_kwargs`, message metadata, or raw content block construction. If LangChain doesn't support it, the FR must specify a workaround (direct API call or monkey-patch). **Spike this before writing production code.**

#### 5. Phase 2 (baseline checkpoint) is premature

Phase 2 requires:
- A new graph (`baseline/graph.yaml`) that reads and "summarizes" all stable context
- Watcher2 integration to inject baseline state
- Clarity on whether baseline is *verbatim* (preserves full context) or *summarized* (lossy, may degrade quality)

This is a separate feature with its own design decisions. Defer to a follow-up FR after Phase 1 proves the caching primitives work. Phase 1 alone (prompt-level caching) gives the 3x reduction within watcher2's ~5-minute Anthropic cache TTL window — the 4 planning steps and 3 enforcement steps will benefit from same-prefix caching without any baseline graph.

#### 6. Phase 3 dropped

Domain-clustered contexts is speculative. No evidence of need. Remove from this FR entirely. Can be proposed as a future FR if Phase 1 metrics demonstrate a remaining gap.

#### 7. Effort underestimated

Phase 1 alone requires:
- Prompt schema extension (string → string | list) with validation
- `prepare_messages()` refactor in `executor_base.py` to handle multi-segment system
- Provider-specific `cache_control` injection spike + implementation
- Tests: cache injectio
