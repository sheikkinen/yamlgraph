# Issues 2026-09-24: swallowed errors, faulty output, uncontrolled fan-outs

**Status:** open. No FRs filed yet.
**Observed at:** `7ae21373` (main), macOS, 12 CPUs.
**Source:** dogfood runs of [`innovation_matrix`](../examples/demos/innovation_matrix/),
then a census of all 202 graphs and 67 map nodes in the repo.

## Summary

One run of the `innovation_matrix` pipeline exited 0 while producing two faulty
outputs. Every failure was recorded — log `[ERROR]` lines, `state.errors`, and
`_error` items in the map output — but nothing between the map fan-in and the
process exit reads those records. The census shows the same shape across the
repo.

## 1. Witnessed run

```bash
PROVIDER=anthropic yamlgraph graph run examples/demos/innovation_matrix/pipeline.yaml \
  --var domain=@<domain-brief.md> --json > run.json 2> run.log
```

Model `claude-haiku-4-5`. The domain brief was a 2.4 KB description of YAMLGraph
and its operator context. The raw `run.json` and `run.log` stayed in gitignored
`tmp/` and are not committed; the timings below come from them.

### 1.1 The input was dropped, so the output is generic

1. [`pipeline.yaml`](../examples/demos/innovation_matrix/pipeline.yaml) has no
   `state:` block, so `--var domain` never reached state. `domain` is absent from
   the final state.
2. Lint reports this as E007, but `graph run` only gates on lint with `--gate`
   (FR-677). The run log has no warning.
3. `{state.domain}` ([pipeline.yaml#L19](../examples/demos/innovation_matrix/pipeline.yaml#L19))
   resolved to `None` without complaint
   ([expressions.py#L24-L51](../yamlgraph/utils/expressions.py#L24-L51)).
4. The generated dimensions are domain-free: "Unlimited digital storage and
   processing power", "Human attention span and cognitive load", "Legacy system
   integration and technical debt". All 25 cells and the synthesis are built on
   them.

### 1.2 Lost branches hidden inside a "complete" synthesis

1. No `max_concurrency` is set, so LangGraph's thread pool used Python's default,
   `min(32, cpu + 4)` = 16 workers on this machine.
2. First wave: 9 requests finished in 22.5–29.4 s; the other 7 hit exactly 30.0 s,
   the FR-708 request timeout
   ([llm_bounds.py#L17-L18](../yamlgraph/utils/llm_bounds.py#L17-L18)). The call
   is non-streaming, so the timeout caps the whole generation; for this prompt it
   sits near the median response time.
3. Across the map, 22 attempts timed out (18 retried, 4 final) against 21
   successes: 51% of attempts were wasted. The SDK retries the identical request,
   so a response that is long rather than stuck fails three times, about 91 s per
   branch.
4. Four branches were lost: `_map_index` 3, 8, 21, 23 (cells C1S4, C2S4, C5S2,
   C5S4). The log line says only `Node _map_expand_all_sub failed`, without the
   index.
5. The error items were placed in `expansions` next to the real results
   ([map_compiler.py#L193-L202](../yamlgraph/compile/map_compiler.py#L193-L202)),
   and the `sorted_add` reducer kept them
   ([state_builder.py#L37](../yamlgraph/models/state_builder.py#L37)).
6. `synthesize` received 21 results plus 4 stringified `PipelineError` reprs,
   under a prompt that states "You have received 25 deep explorations"
   ([synthesize.yaml#L18](../examples/demos/innovation_matrix/prompts/synthesize.yaml#L18)).
   The output cites no failed cell and does not mention the loss.
7. The `run_end` telemetry event reports `dropped_events: 0` and has no failure
   field. The CLI printed its success output
   ([graph_commands.py#L230](../yamlgraph/cli/graph_commands.py#L230)) and exited 0.
8. The map took 120.6 s, against roughly 55 s for two clean waves at the 27 s
   median. The extra time went to branches that failed anyway.

The single-node [`graph.yaml`](../examples/demos/innovation_matrix/graph.yaml)
variant showed the same pattern on haiku: timeout after about 92 s (30 s × 3),
exit 0. On the default provider (inception) it completed.

## 2. Defects by boundary

Scale figures come from the census (202 graphs, 67 map nodes).

- **D1 — map fan-in turns errors into data.** Failed branches become
  `{_map_index, _error}` items in the same list as real results
  ([map_compiler.py#L142-L202](../yamlgraph/compile/map_compiler.py#L142-L202)).
  Of the three error paths, the LLM-failure path omits `_error_type` and stores a
  stringified repr; both exception paths record the failure in `errors` as
  `node="map_subnode"` instead of the failing node. Affects all 67 maps.
- **D2 — `on_error: fail` is not honored inside a map.** The wrapper's
  `except Exception` ([map_compiler.py#L161](../yamlgraph/compile/map_compiler.py#L161))
  catches the raise and returns an error item (witness in the appendix). Six
  census graphs declare `fail` on `extract_items`; 48 map sub-nodes use the
  default handler, which ends the same way.
- **D3 — error items travel downstream as content.** Of the 67 maps, 44 have no
  in-graph consumer. The rest feed 26 consumers: 13 LLM nodes render the reprs
  into their prompts; 11 downstream maps fan out over error items (no `_error`
  check found in `persona_scenarios`, `npc/encounter-multi`, or
  `book_translator`); 2 python nodes ignore `_error`.
- **D4 — the exit code ignores `state.errors`.** None of the 202 graphs reads
  `state.errors`, and the CLI does not read it either: the list is written, never
  read. FR-827 defect 4 was worked around downstream only.
- **D5 — undeclared input is dropped silently.** A missing `{state.X}` resolves
  to `None`, and E007 does not stop a run without `--gate`. Scale not measured
  beyond `innovation_matrix`.
- **D6 — concurrency depends on the host.** Without `max_concurrency` the pool is
  `min(32, cpu + 4)`: 16 here, up to 32 on larger machines. The FR-984 setting
  exists; 1 of 202 graphs uses it.
- **D7 — the timeout cannot tell "stuck" from "long".** FR-708 was meant to catch
  stuck endpoints; on a non-streaming call the same 30 s caps total generation
  time. With streaming it would bound the time between chunks instead.
  Separately, the per-branch `timeout` (FR-069) does not stop the call:
  `cancel_futures` only cancels queued work, so the timed-out thread keeps
  running ([map_compiler.py#L103-L112](../yamlgraph/compile/map_compiler.py#L103-L112)).
  6 of 67 maps set a per-branch timeout.
- **D8 — the model decides how many branches a map creates.** 9 maps fan out
  directly over LLM output; none declares `on_error`, and 4 have no `max_items`,
  including the generator snippet
  [`generate-then-map.yaml`](../examples/yamlgraph_gen/snippets/patterns/generate-then-map.yaml),
  which copies the pattern into generated graphs. Overflow only logs a warning and
  slices the list
  ([map_compiler.py#L355-L361](../yamlgraph/compile/map_compiler.py#L355-L361));
  FR-939 (overflow raises) is judged but not implemented. 18 maps rely on the
  default cap of 100 ([config.py#L57](../yamlgraph/config.py#L57)).
- **D9 — `innovation_matrix` assumes exactly 5 × 5.** "Exactly 5" appears only in
  prompt prose. Cell IDs use `i // 5`
  ([cartesian.py#L33](../examples/demos/innovation_matrix/nodes/cartesian.py#L33)),
  so any other constraint count mislabels cells; `max_items: 25`
  ([pipeline.yaml#L30](../examples/demos/innovation_matrix/pipeline.yaml#L30))
  would silently cut a 5 × 6 grid; the synthesis prompt hard-codes "25" in four
  places.
- **D10 — lint-clean is not compilable.** The safety-guards demo (FR-027
  "Execution Safety") does not compile: a `condition` on the parallel fan-out
  `to: [revise, expand]`
  ([graph.yaml#L82-L83](../examples/demos/safety-guards/graph.yaml#L82-L83)) is
  rejected by `_classify_fanout`
  ([edge_compiler.py#L35](../yamlgraph/compile/edge_compiler.py#L35)). Lint
  reports 0 errors; there is no demo log and no test. The intended wiring is also
  unbalanced: `expand` would run again on every pass of the revise loop.

## 3. Existing protections

- The census demos own completeness in code:
  [corpus_census/tools.py#L243](../examples/demos/corpus_census/tools.py#L243)
  records `_error` items as failed ledger rows,
  [#L292-L294](../examples/demos/corpus_census/tools.py#L292-L294) raises on any
  missing index, and an `ERROR_STRINGS` check catches judgements that are error
  strings. The design is right, but it is re-implemented per graph downstream
  instead of once at the fan-in.
- FR-944's map-to-map barrier; FR-984's concurrency setting; W013 flags dynamic
  maps without `max_items`; W017 flags an explicit `on_error: skip` but not the
  default handler, which has the same effect.

## 4. Candidate FRs

Not filed. Each needs a judgement via `scripts/judge.sh`. One fix at the map
fan-in replaces 26 consumer-side fixes.

1. Separate failures from results at the map fan-in; honor `on_error: fail`; add
   a declared partial-success policy (for example `min_success`). The D2 witness
   is the RED test.
2. Exit non-zero when `state.errors` is non-empty, and add a failure count to
   `run_end`.
3. Reject `--var` keys that are not in state, or make E007 block runs by default.
4. Default `max_concurrency` (or a per-provider limit), so behavior does not
   depend on `os.cpu_count()`.
5. Timeout semantics: stream long generations; do not retry a timed-out request
   unchanged.
6. Implement FR-939; check item counts where the model chooses the fan-out size.
7. CI gate that compiles every graph (would have caught D10).
8. Repair `innovation_matrix/pipeline.yaml` (state block, derived counts, IDs for
   any grid size). It is a graph artifact, so only via `scripts/author.sh`.

## 5. Tooling note

The FR-767 PreToolUse guard denied a read-only `python -c` whose text named
`examples/demos/safety-guards/graph.yaml` ("unrecognized write shape"). The same
compile check ran from a scratch script whose command line names no governed
path. This is a false positive on read-only commands; the guard was not changed.

compile_graph(load_graph_config("examples/demos/safety-guards/graph.yaml")).compile()
# ValueError: Edge 'review' -> ['revise', 'expand'] has a condition on a

Census method: every git-tracked YAML under `examples/`, `graphs/` and
`.chaplain/graphs/` whose top-level `nodes:` is a mapping (202 graphs). For each
map node the scan records the `over` source, `max_items`, the sub-node's
`on_error` and `timeout`, and the other nodes that reference its collect key as
`state.<key>`. It is pattern matching, not compilation, so consumer counts are
approximate.
