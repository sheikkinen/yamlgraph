# Issues 2026-09-24: swallowed errors, faulty output, uncontrolled fan-outs

**Status:** open. No FRs filed yet.
**Observed at:** `7ae21373` (main), macOS, 12 CPUs. D2 and D10 witnesses
re-run and all cited lines re-checked at `1962911d`.
**Source:** dogfood runs of [`innovation_matrix`](../examples/demos/innovation_matrix/),
then a census of all 202 graphs and 67 map nodes in the repo.

## Summary

One run of the `innovation_matrix` pipeline exited 0 while producing two faulty
outputs. Every failure was recorded — log `[ERROR]` lines, `state.errors`, and
`_error` items in the map output — but nothing between the map fan-in and the
process exit reads those records. The census shows the same shape across the
repo.


Model `claude-haiku-4-5`. The domain brief was a 2.4 KB description of YAMLGraph

## 2. Defects by boundary

Scale figures come from the census (202 graphs, 67 map nodes).

- **D1 — map fan-in turns errors into data.** Failed branches become
  `{_map_index, _error}` items in the same list as real results
  ([map_compiler.py#L142-L202](../yamlgraph/compile/map_compiler.py#L142-L202)).
  Of the three error paths, the LLM-failure path omits `_error_type` and stores a
  stringified repr; both exception paths record the failure in `errors` as
  `node="map_subnode"` instead of the failing node. Affects all 67 maps.
- **D2 — `on_error: fail` is not honored inside a map.** The wrapper's
  `except Exception` ([map_compiler.py#L161](../yamlgraph/compile/map_compiler.py#L161))
  catches the raise and returns an error item (witness in the appendix). Six
  census graphs declare `fail` on `extract_items`; 48 map sub-nodes use the
  default handler, which ends the same way.
- **D3 — error items travel downstream as content.** Of the 67 maps, 44 have no
  in-graph consumer. The rest feed 26 consumers: 13 LLM nodes render the reprs
  into their prompts; 11 downstream maps fan out over error items (no `_error`
  check found in `persona_scenarios`, `npc/encounter-multi`, or
  `book_translator`); 2 python nodes ignore `_error`.
- **D4 — the exit code ignores `state.errors`.** None of the 202 graphs reads
  `state.errors`, and the CLI does not read it either: the list is written, never
  read. FR-827 defect 4 was worked around downstream only.
- **D5 — undeclared input is dropped silently.** A missing `{state.X}` resolves
  to `None`, and E007 does not stop a run without `--gate`. Scale not measured
  beyond `innovation_matrix`.
- **D6 — concurrency depends on the host.** Without `max_concurrency` the pool is
  `min(32, cpu + 4)`: 16 here, up to 32 on larger machines. The FR-984 setting
  exists; 1 of 202 graphs uses it.
- **D7 — the timeout cannot tell "stuck" from "long".** FR-708 was meant to catch
  stuck endpoints; on a non-streaming call the same 30 s caps total generation
  time. With streaming it would bound the time between chunks instead.
  Separately, the per-branch `timeout` (FR-069) does not stop the call:
  `cancel_futures` only cancels queued work, so the timed-out thread keeps
  running ([map_compiler.py#L103-L112](../yamlgraph/compile/map_compiler.py#L103-L112)).
  6 of 67 maps set a per-branch timeout.
- **D8 — the model decides how many branches a map creates.** 9 maps fan out
  directly over LLM output; none declares `on_error`, and 4 have no `max_items`,
  including the generator snippet
  [`generate-then-map.yaml`](../examples/yamlgraph_gen/snippets/patterns/generate-then-map.yaml),
  which copies the pattern into generated graphs. Overflow only logs a warning and
  slices the list
  ([map_compiler.py#L355-L361](../yamlgraph/compile/map_compiler.py#L355-L361));
  FR-939 (overflow raises) is judged but not implemented. 18 maps rely on the
  default cap of 100 ([config.py#L57](../yamlgraph/config.py#L57)).
- **D9 — `innovation_matrix` assumes exactly 5 × 5.** "Exactly 5" appears only in
  prompt prose. Cell IDs use `i // 5`
  ([cartesian.py#L33](../examples/demos/innovation_matrix/nodes/cartesian.py#L33)),
  so any other constraint count mislabels cells; `max_items: 25`
  ([pipeline.yaml#L30](../examples/demos/innovation_matrix/pipeline.yaml#L30))
  would silently cut a 5 × 6 grid; the synthesis prompt hard-codes "25" in four
  places.
- **D10 — lint-clean is not compilable.** The safety-guards demo (FR-027
  "Execution Safety") does not compile: a `condition` on the parallel fan-out
  `to: [revise, expand]`
  ([graph.yaml#L82-L83](../examples/demos/safety-guards/graph.yaml#L82-L83)) is
  rejected by `_classify_fanout`
  ([edge_compiler.py#L35](../yamlgraph/compile/edge_compiler.py#L35)). Lint
  reports 0 errors; there is no demo log and no test. The intended wiring is also
  unbalanced: `expand` would run again on every pass of the revise loop.

## 4. Census failure model

Target behavior for a large census: about 95% of items succeed first time,
about 4% succeed on retry, and about 1% fail permanently (bad data, site down).
Retries must not redo the 95%. After 2–3 attempts the missing 1% is part of the
result, and a declared policy says whether that result is good enough.

### 4.1 What LangGraph provides (probed on 1.2.11)

Probe: 100 `Send` branches; 4 fail once and then succeed; 1 always fails.

| Primitive | Observed | Fits |
|---|---|---|
| `RetryPolicy(max_attempts=3)` on the node | Retries only the failing branch: flaky items 2 calls each, healthy items 1, the permanent item 3 | Yes |
| `default_retry_on` | Retries `ConnectionError` and HTTP 5xx; does not retry `ValueError`, `TypeError`, `LookupError`, `OSError` and similar | Yes: a site that is down is retried, bad data is not |
| Checkpointer + `invoke(None)` resume | When the step fails, the 99 finished branches stay in the checkpoint as pending writes; resume re-ran 1 branch and ended with 100 results | Yes: no rework |
| `add_node(..., error_handler=...)` ("give up and continue") | Fires only when the failing task is the only task in its step. With 1 branch the handler recorded the failure; with 2 or 100 branches the step raised `ConnectionError` and the step after the map never ran. Only the single-task inline path in `langgraph/pregel/_runner.py` (L222–L230) routes to the handler | **No**, for any real map |

Trap: forcing the graph past the failure with
`update_state(cfg, {...}, as_node="work")` discarded the 99 pending writes
without an error. The run completed with `results: 0`, a wrong answer that
looks right (witness in the appendix).

### 4.2 The pattern that meets the target

1. Each branch retries itself (attempts, backoff, transient errors only). After
   the last attempt it *returns* a failure record `{index, item_ref, error_type,
   attempts}` instead of raising, so it cannot block the other branches.
2. Failure records go in their own channel, never in the results list.
3. The fan-in asserts `results + failures == dispatched`, so no branch vanishes
   without a record, and a policy such as `min_success` records whether the
   run is good enough. The output is produced either way.
4. Resume on two levels: a checkpointer restarts a crashed run without rework;
   a ledger keyed by item ID (as `corpus_census` already keeps) re-runs only
   the missing items on a later run, for example when the site is back.

Probe of this pattern: 99 results, 1 failure record, 106 calls, every healthy
item called once. At 10,000 items with a 95/4/1 split that is
9,500 + 800 + 300 = 10,600 calls, about 6% overhead.

### 4.3 Where yamlgraph stands

- `wrap_for_reducer` already catches errors inside the branch, which is the
  right place, but it puts failures into the results list (D1) and nothing
  checks completeness.
- Retries happen in the provider SDK (`max_retries=2`), which resends the
  identical request, timeouts included (D7). Whether a map branch separates
  transient from permanent errors was not checked.
- There is no checkpointer unless the graph declares one
  ([graph_loader.py#L436-L450](../yamlgraph/compile/graph_loader.py#L436-L450)),
  so a crash mid-census redoes everything. Resume of a killed process with a
  checkpointer was not tested.
- LangGraph's retry-then-raise alone gives no finished result when some items
  fail permanently, and its `error_handler` does not fire for concurrent
  branches, so neither can be the base; retry-then-degrade inside the branch
  can.

## 6. Root cause

No single mechanism in §5.1 is complete. The closest to right is a combination:
file-hook's `.md` twin (the output's existence is the state, so re-runs skip
done items, as in `make`) plus the census ledger (failures are explicit rows and
completeness is asserted). Each graph that built one of these first had to
invent an item key locally: the file name, the Wikidata QID, the census row ID.

The map is missing three concepts, in causal order:

1. **Item identity.** `_map_index` is a position in a list, not a stable key.
   Without a key nothing can be cached, compared between runs, retried
   selectively, or deduplicated.
2. **A failure channel.** Failures travel in the results list (D1), so no store
   can persist results safely: it would persist failures as successes (§5.1,
   row 2).
3. **Cross-run scope.** The checkpointer is scoped to one thread and answers
   "resume this run". A census needs "do not redo what any earlier run already
   did".

Not the root cause:

- **YAML complexity.** The map surface (`over`, `as`, `node`, `collect`) is
  small. What it lacks is meaning, not syntax.
- **Missing extension points.** Tool nodes before and after a map can already
  partition and merge. That is why four graphs built their own version: the
  extension point exists, the shared building block does not. Generic pre/post
  hooks would add a fifth reinvention with nicer syntax.

The cure is a declared `key:` on the map that the compiler expands into a fixed
layer order inside each branch, plus one ledger step after the fan-in:

```text
branch:   degrade( retry( cache( work(item) ) ) )
            |        |       |
            |        |       looked up by (key, version, node version) (§6.3)
            |        transient errors only, in the existing executor loop
            failure record into the failures channel (fix A)
fan-in:   completeness assert + ledger write (new / changed / unchanged /
          deleted / failed)
```

The map wrapper (`wrap_for_reducer`) owns cache, degrade and completeness.
Retry stays where it already is, in the executor's call loop
([executor.py#L150-L178](../yamlgraph/executor.py#L150-L178)), amended by A.2.
LangGraph's own primitives cannot be stacked this way (checked against the
1.2.11 source, not by a run):

- The map registers `wrap_for_reducer(...)` as its only node
  ([map_compiler.py#L329-L332](../yamlgraph/compile/map_compiler.py#L329-L332)).
  `CachePolicy` has only `key_func` and `ttl`, no predicate to skip a result,
  so a policy on that node would cache degraded failure records.
- `RetryPolicy` retries only when the exception leaves the node; degrading
  requires that it does not, and `error_handler` does not fire for concurrent
  branches (§4.1).

LangGraph supplies `Send`, the checkpoint's pending writes, and storage classes
(`SqliteCache` and friends, called directly rather than through
`CachePolicy`). Everything the lookup needs is known at fan-out (§6.3), so the
wrapper looks up before work, stores only on success, and degrades on the
final exception. Successes are stored, failures are not, and the next run
re-executes only the failures. That meets §4: the 95% are reused, retry
recovers the 4%, the 1% stays in the failures channel after 2–3 runs.

The same design serves repeated runs over one subject: a changed item keeps its
key but carries a new version and is reprocessed; an unchanged one is reused.
The store cannot report deletions or give a human-readable diff; the ledger
does. Prior art: dbt incremental models (`unique_key` with an
`is_incremental` filter), make and Bazel rebuilds.

### 6.1 Syntax today and after A + J

Today (every comment is a defect or a gap from §2 and §5):

```yaml
nodes:
  judge_items:
    type: map
    over: "{state.items}"
    as: item
    max_items: 10000       # overflow is silently sliced (D8)
    timeout: 120           # the timed-out thread keeps running (D7)
    on_error: fail         # documented as "raises"; returns an _error row (D2)
    node:
      type: llm
      prompt: judge_item
      state_key: judgement
      on_error: retry      # no backoff, every error type, on top of SDK retries
      max_retries: 3
      cache: {ttl: 86400}  # accepted, inert (§5.1 row 2)
    collect: judgements    # results and _error rows mixed (D1)
```

After the two FRs in §7: one config block and four map keys; existing keys keep
their names and gain the meaning they claim. Map-level `on_error` is folded into
`min_success`: `fail` means `min_success: 1.0`, judged at the fan-in after
every branch has finished, never a raise in the middle of the step.

```yaml
config:
  cache: {type: sqlite, path: .cache/yamlgraph.db}   # result store, used by the map wrapper

nodes:
  judge_items:
    type: map
    over: "{state.items}"
    as: item
    key: "{state.item.id}"                # identity, not position
    version: "{state.item.etag}"          # optional; default hash of the item (§6.3)
    max_items: 10000                     # FR-939: overflow raises
    cache: true                          # reuse by (key, version, node version); no ttl
    node:
      type: llm
      prompt: judge_item
      state_key: judgement
      on_error: retry                    # see §7 A.2 for which layer retries what
      max_retries: 3
    collect: judgements                  # successes only
    failures: judgement_failures         # degrade layer
    min_success: 0.98                    # verdict at the fan-in (§7 A.3, A.4)
    ledger: outputs/judge.ledger.jsonl
```

### 6.2 Two stores, two questions

| Store | Answers | Backend | Why |
|---|---|---|---|
| Cache | "Do not pay twice for the same question" | SQLite by default, Redis optional; `config.cache.type` mirrors the existing memory/sqlite/redis checkpointer options | Needs indexed lookup and concurrent writers; LangGraph's `SqliteCache`/`RedisCache` classes, called by the wrapper (§6). Once it holds the only copy of a result it is a result store: no TTL, no eviction (component D's warning) |
| Ledger | "What changed, failed or disappeared since the last run" | JSONL, one snapshot file per run, one row per key | Read and diffed by people; the census artifact, not a lookup structure. `deleted` is computed against the previous run's snapshot |

- JSONL is not a cache: every lookup is a scan and there is no TTL.
- No per-graph caches. The graph-local ones in §5.1 exist because the
  building block was missing. A new backend, if ever needed, is one registered
  `BaseCache` implementation behind `config.cache.type`.

Ledger row:

```json
{"key": "repo-42", "version": "etag:\"9f…\"", "node_version": "sha256:1a…", "status": "unchanged", "attempts": 0, "run": "2026-09-24T10:00Z"}
```

`status` is `new`, `changed`, `unchanged`, `failed` or `deleted`. `deleted`
means the key was in the previous snapshot but not in `over`; it is the one
fact the store cannot hold. Two concurrent runs writing one ledger path is an
error, not a merge.

### 6.3 Key, version, node version

Items carry their own identity and version; the framework hashes only what it
must.

| Part | Answers | Source | Cost |
|---|---|---|---|
| `key:` (required with `ledger:`) | Which item | The item's own ID (`{state.item.id}`, a URL, a path) | Declared |
| `version:` (optional) | Did this item change | The source's own signal: mtime or git blob SHA, HTTP ETag, Wikidata revision ID, `updated_at`. Default: hash of the item's canonical JSON | One hash of data in hand |
| Node version (computed) | Did the question change | Hash of the sub-node's definition plus its non-item inputs, computed once per map run at fan-out | One hash per run |

Reuse when all three match; otherwise run. `changed` in the ledger means same
key, different `version`; a new node version re-runs every item and the
ledger records why.

Node version, per part:

- **Inputs.** Declared `variables:` are not the whole input: `execute_prompt`
  also receives the full branch state
  ([llm_nodes.py#L345-L360](../yamlgraph/node_factory/llm_nodes.py#L345-L360)),
  and templates may read `{{ state.x }}` directly. Python, tool, agent and
  subgraph sub-nodes receive the full state as well. The inputs are therefore
  the branch state minus the item, and only FR-955's projection makes that set
  small. Without FR-955 the only safe set is the whole parent state, where any
  unrelated field change re-runs every item. Reuse (J) therefore lands after
  FR-955; the branch contract (A) needs only `key:` and does not.
- **Definition.** LLM: prompt file, output schema, and the *resolved* provider
  and model (FR-940 allows `{state.x}` and environment defaults, so the
  declared value is not enough). Python and tool: the source file of the
  function. Agent and subgraph: a declared `node_version:` string is required
  when `cache:` is on; lint rejects the combination without it.
- **Failures.** A permanent failure is not a result, but re-paying it on every
  run is waste. Open for the judge: store `failed` with its version so an
  unchanged bad item is skipped until its version changes, or re-run it every
  time (simpler; §4 assumed this).

- The item's producer knows best whether it changed, so the version is
  normalised where the data enters. Remote data (URL, API) is the ordinary
  case: the adapter puts the ETag or revision in `version`; no TTL needed.
- Coarse invalidation is deliberate: a prompt edit or a changed shared
  variable re-runs everything. For a census a new question means new answers.
- Duplicate keys in `over` raise at fan-out.
- `--refresh` bypasses reuse, for resampling at temperature > 0 or evicting a
  known-bad result.
- A first draft hashed the fully rendered request per item. That needed the
  prompt rendered below the wrapper, worked only for LLM nodes, and made
  unstable prompt values (timestamps) silent cache misses. Withdrawn.

Settled by source reading, not by a run: a node-level `CachePolicy` on the map
sub-node would cache failure records (§6). Unverified, needs a witness before
an FR claims it: `SqliteCache` used directly by the wrapper, with concurrent
branches and across processes.

### 6.4 Prior art: component D

[docs/plan-web-toolkit.md](plan-web-toolkit.md#component-d-resumable-storage-backed-map-primitive)
already plans a "resumable storage-backed map" and maps its contract to
LangGraph natives (rev 8). FR-936's non-overlap contract assigns `CachePolicy`,
Store-backed results and resume to it, outside all four FR-936 children. No FR
exists. §6.1–§6.3 re-derived part of D; D names two gaps this document had
missed:

- **Chunked scheduling.** `Send` schedules every branch in one step; at
  census scale that is unbounded memory.
- **Results out of state.** A `collect` list of 10k–500k items lives in the
  state channel and in every checkpoint. Results belong in the store; the
  fan-in reads the store.

D's witness is the one to keep: `kill -9` mid-run, re-run, prove finished items
are not re-executed and the output equals an uninterrupted run.

Branch input projection
([FR-955](../feature-requests/FR-955-map-branch-input-projection.md)) is a
prerequisite for D: without it every branch checkpoints a copy of the whole
parent state, and the node version has no bounded input set (§6.3).

### 6.5 Implementation shape: does the map need to become a package?

Yes, as a separate move-only refactor before A.

[map_compiler.py](../yamlgraph/compile/map_compiler.py) is 368 lines today
(target 400, cap 450) with four functions: `flatten_map_results`,
`_execute_node_fn`, `wrap_for_reducer` and `compile_map_node`. A and J add
roughly: key, version and duplicate check at fan-out; one failure-record
helper (net smaller, it replaces three error paths); store lookup; node
version; a fan-in node with completeness and `min_success`; the ledger. That
takes the file well past the cap, and the pieces have different change rates.

What the code shows beyond size:

- **There is no fan-in node.** The map compiles to an edge function that
  returns `Send`s, plus one sub-node; the edge out of a map is
  `sub_node → target`
  ([edge_compiler.py#L246-L249](../yamlgraph/compile/edge_compiler.py#L246-L249)).
  Completeness, `min_success` and the ledger need a synthetic
  `_map_{name}_join` node. Precedent: FR-944's map-to-map barrier join
  ([edge_compiler.py#L221-L236](../yamlgraph/compile/edge_compiler.py#L221-L236)).
  The join cannot be told the dispatched count by the edge function (an edge
  writes no state); it re-resolves `over` and the keys from the merged state.
- **The map's compiled identity is a tuple `(edge_fn, sub_node_name)`**,
  unpacked at seven sites in `edge_compiler.py`, one in `routing.py`, one in
  `node_compiler.py`. Adding a join name changes that shape at all of them. A
  small typed record (`CompiledMap`) in the refactor makes the later change a
  one-field addition. It is the one non-move change the refactor carries.
- **`wrap_for_reducer` normalises results twice** (the non-dict and dict
  paths repeat `model_dump` plus `_map_index`), and its error-in-result check
  tests key presence (`"errors" in result`), so a successful update that
  carries `errors: []` would be recorded as a failure. The first is removed in
  the move; the second is a behavior change and belongs to A with a RED test.
- **The sub-node factory** (the `if/elif` over five node types, ~70 lines) is
  unrelated to the branch contract and changes only when a node type is added.

Proposed package, `yamlgraph/compile/map/`:

| Module | Holds | Changed by |
|---|---|---|
| `__init__.py` | `compile_map_node`, `CompiledMap` | refactor |
| `subnode.py` | sub-node factory dispatch | new node types |
| `fan_out.py` | resolve `over`, overflow (F), key, version, duplicates, node version, `Send` | F, A, J |
| `branch.py` | `wrap_for_reducer`, `_execute_node_fn`, result normalisation, failure record | A, E |
| `fan_in.py` | join node: completeness, `min_success` | A |
| `store.py` | result store lookup and write | J |
| `ledger.py` | per-run snapshot, diff against the previous one | J |
| `results.py` | `flatten_map_results` | — |

The refactor is move-only plus `CompiledMap`, green before and after, and
needs no new tests beyond an import-path update; it is filed with A or just
before it, not folded into A's diff. Retry is not in the package: it stays in
the executor and node error handlers (A.2).

### A. Map branch contract (D1, D2, D3); supersedes FR-957

Implements the §4.2 pattern in `wrap_for_reducer`
([map_compiler.py#L137-L202](../yamlgraph/compile/map_compiler.py#L137-L202)),
which owns key, lookup, degrade and completeness (§6):

0. The map declares an optional `key:` expression (default: `_map_index`) and
   an optional `version:` (§6.3). Failure records, results and the ledger
   carry the key. Duplicate keys raise at fan-out.
1. Failed branches write a failure record `{_map_index, key, error_type,
   attempts, node}` to a separate failures channel (and `state.errors`), never
   into `collect`. The three error paths share one helper, which also fixes the
   missing `_error_type` on the L193 path and the `map_subnode` node name.
2. Retry is not added to the wrapper. Three retry layers already exist for an
   LLM sub-node, nested:

   | Layer | Where | Retries | Backoff |
   |---|---|---|---|
   | SDK | `max_retries=2` in `llm_bounds.py` | the SDK's own choice | SDK |
   | Executor loop | [executor.py#L150-L178](../yamlgraph/executor.py#L150-L178), `MAX_RETRIES=3` | `is_retryable` ([executor_base.py#L67-L87](../yamlgraph/executor_base.py#L67-L87)) | exponential, jitter |
   | Node handler | `on_error: retry` → `handle_retry` ([error_handlers.py#L108-L135](../yamlgraph/error_handlers.py#L108-L135)), `max_retries` (default 3) | every error, with validation feedback | none |

   A.2 gives each layer one job:
   - SDK retries off, so the executor loop is the single owner of transient
     errors. This applies to every LLM call, not only map branches.
   - `is_retryable` matches class names, including the substring
     `"rate" in name`, which also matches unrelated names. Replace it with an
     explicit per-provider mapping into transient (connection errors, HTTP
     5xx, 429 honouring `Retry-After`) and permanent (validation, other 4xx,
     bad data).
   - `APITimeoutError` is on the retryable list today. Timeouts on
     non-streaming calls are not retried: they cannot tell long from stuck
     (E.1).
   - The node handler keeps what only it can do, re-asking with validation
     feedback, and stops re-running errors the executor already classified
     as transient-exhausted or permanent. Otherwise the layers multiply.
   - The final exception is typed and carries attempts and error class; the
     wrapper turns it into the failure record.
   - Unverified: the nesting allows up to 3 × 3 × 3 attempts per branch, but
     the witnessed run showed about 91 s (3 × 30 s). Which layers actually ran
     must be established before the FR claims a count.
3. A synthetic join node (§6.5) asserts `results + failures == dispatched`.
   `min_success` (count or fraction) decides whether the run is good enough,
   and the verdict is recorded for B; what consumers see below it is open
   (A.4). An earlier draft of this document
   proposed "any failed branch raises" as the default; for a census that
   discards 99% of finished work over 1% of bad items, so it is withdrawn.
4. `on_error: fail` (map or sub-node) means `min_success: 1.0`, judged at the
   fan-in; finished branches are kept. One way to say it, not two.

   Open for the judge: what consumers see below `min_success`, and the
   default when `min_success` is absent. "Output always produced" hands a
   consumer 21 of 25 items without saying so; D3's wrong answer changes form
   instead of going away, and H fixes only one of 26 consumers. The options
   are to raise at the fan-in, or to make consumers read `failures`. Raising is
   cheap only once J makes a re-run reuse finished work, so the default
   depends on whether J has landed.
5. Migrate [corpus_census/tools.py#L243](../examples/demos/corpus_census/tools.py#L243),
   which reads `_error` items from the collect list, to the failures channel.

RED: the D2 witness; a test that the L193 path records `_error_type`; a
successful update carrying `errors: []` is collected as a result (§6.5); a
95/4/1 fixture asserting call counts (healthy items called once) and the
completeness invariant. Preceded by the §6.5 move-only refactor.

### J. Resumable map: component D (§6, §6.4)

Investigation FR first (`investigation_before_fix`). Two design choices are
open and dominate the cost:

- **Where results live.** 26 consumers read `collect` from state. Either they
  all change to read the store, or the fan-in copies results back into state,
  which returns the 500k-item problem to the checkpoint.
- **Chunked scheduling.** Bounded `Send` batches change the compiled shape
  from one map edge to a batch loop.

The fix FR then covers:

- `config.cache` selects the result store (§6.2). The wrapper looks up
  `(key, version, node version)` (§6.3) before work and stores only on
  success; no `CachePolicy`, no TTL. `cache:` sits on the map, not the
  sub-node; FR-032's node-level `cache:` stays inert inside a map and lint
  says so. Fix `examples/demos/cache`, whose claim is false today.
- After the fan-in, write the per-run JSONL snapshot (§6.2). It replaces the
  graph-local versions (census, file-hook, self-portrait) as they are touched.
- `--refresh` bypasses reuse.
- Lint: `ledger:` without `key:` is an error; `cache:` on an agent or
  subgraph sub-node without `node_version:` is an error (§6.3).
- Lands after A (the failure channel keeps failures out of the store) and
  after FR-955 (checkpoint size).
- RED: the §6.3 `SqliteCache` witness first; then a two-run fixture where
  run 2 changes one item's version, deletes one and restores a failed one,
  asserting exactly those three are executed and the ledger classifies all
  five states; a node-version change re-runs all; then D's `kill -9` resume
  witness.
