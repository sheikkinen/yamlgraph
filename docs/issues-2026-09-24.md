# Issues 2026-09-24: swallowed errors, faulty output, uncontrolled fan-outs

**Status:** open. No FRs filed yet.
**Observed at:** `7ae21373` (main), macOS, 12 CPUs. D2 and D10 witnesses
re-run and all cited lines re-checked at `1962911d`.
**Source:** dogfood runs of [`innovation_matrix`](../examples/demos/innovation_matrix/),
then a census of all 202 graphs and 67 map nodes in the repo.

## Summary

One run of the `innovation_matrix` pipeline exited 0 while producing two faulty
outputs. Every failure was recorded — log `[ERROR]` lines, `state.errors`, and
`_error` items in the map output — but nothing between the map fan-in and the
process exit reads those records. The census shows the same shape across the
repo.

## 1. Witnessed run

```bash

  --var domain=@<domain-brief.md> --json > run.json 2> run.log
```

Model `claude-haiku-4-5`. The domain brief was a 2.4 KB description of YAMLGraph
and its operator context. The raw `run.json` and `run.log` stayed in gitignored

## 2. Defects by boundary

Scale figures come from the census (202 graphs, 67 map nodes).

- **D1 — map fan-in turns errors into data.** Failed branches become
  `{_map_index, _error}` items in the same list as real results
  ([map_compiler.py#L142-L202](../yamlgraph/compile/map_compiler.py#L142-L202)).
  Of the three error paths, the LLM-failure path omits `_error_type` and stores a
  stringified repr; both exception paths record the failure in `errors` as
  `node="map_subnode"` instead of the failing node. Affects all 67 maps.
- **D2 — `on_error: fail` is not honored inside a map.** The wrapper's
  `except Exception` ([map_compiler.py#L161](../yamlgraph/compile/map_compiler.py#L161))
  catches the raise and returns an error item (witness in the appendix). Six
  census graphs declare `fail` on `extract_items`; 48 map sub-nodes use the
  default handler, which ends the same way.
- **D3 — error items travel downstream as content.** Of the 67 maps, 44 have no
  in-graph consumer. The rest feed 26 consumers: 13 LLM nodes render the reprs
  into their prompts; 11 downstream maps fan out over error items (no `_error`
  check found in `persona_scenarios`, `npc/encounter-multi`, or
  `book_translator`); 2 python nodes ignore `_error`.
- **D4 — the exit code ignores `state.errors`.** None of the 202 graphs reads
  `state.errors`, and the CLI does not read it either: the list is written, never
  read. FR-827 defect 4 was worked around downstream only.
- **D5 — undeclared input is dropped silently.** A missing `{state.X}` resolves
  to `None`, and E007 does not stop a run without `--gate`. Scale not measured
  beyond `innovation_matrix`.
- **D6 — concurrency depends on the host.** Without `max_concurrency` the pool is
  `min(32, cpu + 4)`: 16 here, up to 32 on larger machines. The FR-984 setting
  exists; 1 of 202 graphs uses it.
- **D7 — the timeout cannot tell "stuck" from "long".** FR-708 was meant to catch
  stuck endpoints; on a non-streaming call the same 30 s caps total generation
  time. With streaming it would bound the time between chunks instead.
  Separately, the per-branch `timeout` (FR-069) does not stop the call:
  `cancel_futures` only cancels queued work, so the timed-out thread keeps
  running ([map_compiler.py#L103-L112](../yamlgraph/compile/map_compiler.py#L103-L112)).
  6 of 67 maps set a per-branch timeout.
- **D8 — the model decides how many branches a map creates.** 9 maps fan out
  directly over LLM output; none declares `on_error`, and 4 have no `max_items`,
  including the generator snippet
  [`generate-then-map.yaml`](../examples/yamlgraph_gen/snippets/patterns/generate-then-map.yaml),
  which copies the pattern into generated graphs. Overflow only logs a warning and
  slices the list
  ([map_compiler.py#L355-L361](../yamlgraph/compile/map_compiler.py#L355-L361));
  FR-939 (overflow raises) is judged but not implemented. 18 maps rely on the
  default cap of 100 ([config.py#L57](../yamlgraph/config.py#L57)).
- **D9 — `innovation_matrix` assumes exactly 5 × 5.** "Exactly 5" appears only in
  prompt prose. Cell IDs use `i // 5`
  ([cartesian.py#L33](../examples/demos/innovation_matrix/nodes/cartesian.py#L33)),
  so any other constraint count mislabels cells; `max_items: 25`
  ([pipeline.yaml#L30](../examples/demos/innovation_matrix/pipeline.yaml#L30))
  would silently cut a 5 × 6 grid; the synthesis prompt hard-codes "25" in four
  places.
- **D10 — lint-clean is not compilable.** The safety-guards demo (FR-027
  "Execution Safety") does not compile: a `condition` on the parallel fan-out
  `to: [revise, expand]`
  ([graph.yaml#L82-L83](../examples/demos/safety-guards/graph.yaml#L82-L83)) is
  rejected by `_classify_fanout`
  ([edge_compiler.py#L35](../yamlgraph/compile/edge_compiler.py#L35)). Lint
  reports 0 errors; there is no demo log and no test. The intended wiring is also
  unbalanced: `expand` would run again on every pass of the revise loop.

## 4. Census failure model

Target behavior for a large census: about 95% of items succeed first time,
about 4% succeed on retry, and about 1% fail permanently (bad data, site down).
Retries must not redo the 95%. After 2–3 attempts the missing 1% is part of the
result, and a declared policy says whether that result is good enough.

### 4.1 What LangGraph provides (probed on 1.2.11)

Probe: 100 `Send` branches; 4 fail once and then succeed; 1 always fails.

| Primitive | Observed | Fits |
|---|---|---|
| `RetryPolicy(max_attempts=3)` on the node | Retries only the failing branch: flaky items 2 calls each, healthy items 1, the permanent item 3 | Yes |
| `default_retry_on` | Retries `ConnectionError` and HTTP 5xx; does not retry `ValueError`, `TypeError`, `LookupError`, `OSError` and similar | Yes: a site that is down is retried, bad data is not |
| Checkpointer + `invoke(None)` resume | When the step fails, the 99 finished branches stay in the checkpoint as pending writes; resume re-ran 1 branch and ended with 100 results | Yes: no rework |
| `add_node(..., error_handler=...)` ("give up and continue") | Fires only when the failing task is the only task in its step. With 1 branch the handler recorded the failure; with 2 or 100 branches the step raised `ConnectionError` and the step after the map never ran. Only the single-task inline path in `langgraph/pregel/_runner.py` (L222–L230) routes to the handler | **No**, for any real map |

Trap: forcing the graph past the failure with
`update_state(cfg, {...}, as_node="work")` discarded the 99 pending writes
without an error. The run completed with `results: 0`, a wrong answer that
looks right (witness in the appendix).

### 4.2 The pattern that meets the target

1. Each branch retries itself (attempts, backoff, transient errors only). After
   the last attempt it *returns* a failure record `{index, item_ref, error_type,
   attempts}` instead of raising, so it cannot block the other branches.
2. Failure records go in their own channel, never in the results list.
3. The fan-in asserts `results + failures == dispatched`, so no branch vanishes
   without a record, and a policy such as `min_success` records whether the
   run is good enough. The output is produced either way.
4. Resume on two levels: a checkpointer restarts a crashed run without rework;
   a ledger keyed by item ID (as `corpus_census` already keeps) re-runs only
   the missing items on a later run, for example when the site is back.

Probe of this pattern: 99 results, 1 failure record, 106 calls, every healthy
item called once. At 10,000 items with a 95/4/1 split that is
9,500 + 800 + 300 = 10,600 calls, about 6% overhead.

### 4.3 Where yamlgraph stands

- `wrap_for_reducer` already catches errors inside the branch, which is the
  right place, but it puts failures into the results list (D1) and nothing
  checks completeness.
- Retries happen in the provider SDK (`max_retries=2`), which resends the
  identical request, timeouts included (D7). Whether a map branch separates
  transient from permanent errors was not checked.
- There is no checkpointer unless the graph declares one
  ([graph_loader.py#L436-L450](../yamlgraph/compile/graph_loader.py#L436-L450)),
  so a crash mid-census redoes everything. Resume of a killed process with a
  checkpointer was not tested.
- LangGraph's retry-then-raise alone gives no finished result when some items
  fail permanently, and its `error_handler` does not fire for concurrent
  branches, so neither can be the base; retry-then-degrade inside the branch
  can.

## 6. Root cause

No single mechanism in §5.1 is complete. The closest to right is a combination:
file-hook's `.md` twin (the output's existence is the state, so re-runs skip
done items, as in `make`) plus the census ledger (failures are explicit rows and
completeness is asserted). Each graph that built one of these first had to
invent an item key locally: the file name, the Wikidata QID, the census row ID.

The map is missing three concepts, in causal order:

1. **Item identity.** `_map_index` is a position in a list, not a stable key.
   Without a key nothing can be cached, compared between runs, retried
   selectively, or deduplicated.
2. **A failure channel.** Failures travel in the results list (D1), so no store
   can persist results safely: it would persist failures as successes (§5.1,
   row 2).
3. **Cross-run scope.** The checkpointer is scoped to one thread and answers
   "resume this run". A census needs "do not redo what any earlier run already
   did".

Not the root cause:

- **YAML complexity.** The map surface (`over`, `as`, `node`, `collect`) is
  small. What it lacks is meaning, not syntax.
- **Missing extension points.** Tool nodes before and after a map can already
  partition and merge. That is why four graphs built their own version: the
  extension point exists, the shared building block does not. Generic pre/post
  hooks would add a fifth reinvention with nicer syntax.

The cure is a declared `key:` on the map that the compiler expands into a fixed
layer order inside each branch, plus one ledger step after the fan-in:

```text
branch:   degrade( retry( cache( work(item) ) ) )
            |        |       |
            |        |       keyed by hash(item, prompt version, model)
            |        transient errors only
            failure record into the failures channel (fix A)
fan-in:   completeness assert + ledger write (new / changed / unchanged /
          deleted / failed)
```

LangGraph writes a cache entry only when a node returns, so the cache must sit
inside the degrade layer: successes are cached, failures are not, and the next
run re-executes only the failures. That meets §4: the 95% hit the cache, retry
recovers the 4%, the 1% stays in the failures channel after 2–3 runs.

The same key serves repeated runs over one subject: a changed item hashes to a
new key and is reprocessed, an unchanged one hits the cache. The prompt version
must be part of the key, or a prompt change silently reuses stale outputs. The
cache cannot report deletions or give a human-readable diff; the ledger does.
Prior art: dbt incremental models (`unique_key` with an `is_incremental`
filter), make and Bazel content-addressed rebuilds.

Unverified, each needs a witness before an FR claims it:

- `CachePolicy` with `SqliteCache` on `Send` branches, across processes. Only
  `InMemoryCache` on a single node in one process was probed.
- No cache entry is written for a branch whose inner call raises and whose
  outer layer degrades.
- A prompt-version hash exists to put in `key_func`; yamlgraph has none today.

### A. Map fan-in contract (D1, D2, D3)

Implements the §4.2 pattern in `wrap_for_reducer`
([map_compiler.py#L137-L202](../yamlgraph/compile/map_compiler.py#L137-L202)):

0. The map declares an optional `key:` expression (default: `_map_index`).
   Failure records, results and the ledger carry it (§6, concept 1).
1. Failed branches write a failure record `{_map_index, key, error_type,
   attempts, node}` to a separate failures channel (and `state.errors`), never
   into `collect`. The three error paths share one helper, which also fixes the
   missing `_error_type` on the L193 path and the `map_subnode` node name.
2. Per-branch retry in the wrapper: `max_attempts`, backoff, transient errors
   only. The SDK's identical-request retry on timeouts is turned off for map
   branches (overlaps E).
3. The fan-in asserts `results + failures == dispatched`. `min_success` (count
   or fraction) decides whether the run is good enough; the output is always
   produced and the verdict recorded for B. An earlier draft of this document
   proposed "any failed branch raises" as the default; for a census that
   discards 99% of finished work over 1% of bad items, so it is withdrawn.
4. A sub-node declaring `on_error: fail` re-raises instead of returning a
   failure record.
5. Migrate [corpus_census/tools.py#L243](../examples/demos/corpus_census/tools.py#L243),
   which reads `_error` items from the collect list, to the failures channel.

RED: the D2 witness; a test that the L193 path records `_error_type`; a
95/4/1 fixture asserting call counts (healthy items called once) and the
completeness invariant.

### B. Exit code reflects `state.errors` (D4)

- The CLI exits with a distinct code (for example 3, "completed with errors",
  separate from a crash) when the final `state.errors` is non-empty; `run_end`
  gains an `error_count` field.
- Open question for the judge: errors deliberately tolerated with
  `on_error: skip` must either stop appending to `errors` or be counted
  separately, or B punishes graphs that opted in to skipping.
- Depends on A: with a strict map default, map failures already raise; B
  covers the errors that are not raised.

RED: a graph whose `on_error: skip` node fails; assert the exit code.

### C. Reject undeclared input at the boundary (D5)

- `graph run` refuses `--var` keys that are not declared state keys and lists
  the declared ones. This is where external data enters.
- Making a missing `{state.X}` raise instead of resolving to `None` has a much
  larger blast radius. It needs its own FR and a census of graphs that rely on
  the `None` behavior.

RED: `innovation_matrix/pipeline.yaml` with `--var domain=x` is rejected.

### D. Default `max_concurrency` (D6), as an FR-984 amendment

- A config default (for example 8, overridable per graph and by environment
  variable) applied to the run config in the executor, so behavior no longer
  depends on `os.cpu_count()`.

RED: patch `cpu_count` to 64; assert the pool size stays at the default.

### E. Timeout semantics (D7)

1. "Long" versus "stuck": short term, stop retrying timeouts unchanged (the SDK
   retries timed-out requests; limit retries to connection and 5xx errors).
   Longer term, stream LLM responses so the FR-708 timeout bounds the gap
   between chunks, not the whole generation; that is a separate, larger FR.
2. Leaked per-branch threads: a Python thread cannot be killed. Pass the
   branch `timeout` down into the LLM client's request timeout, and document
   that FR-069 bounds the wait, not the work.

### J. Incremental re-run over a keyed map (§6)

  deleted since the last run, or failed with attempts. The ledger replaces the

- Lands after A: before A, the cache would store failure rows as successes.
