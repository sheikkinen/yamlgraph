# 2026-06-28 — Latest Developments in AI Orchestration, and What Matters for YAMLGraph

> Research + reflection. Maps the 2025→2026 orchestration frontier against
> YAMLGraph's capability registry, and ranks the gaps worth closing.

## Sources

- Anthropic, *Building effective agents* (Dec 2024) — the canonical workflow taxonomy.
- Anthropic, *Effective context engineering for AI agents* (Sep 2025) — the field's
  pivot from prompt engineering to context engineering.
- YAMLGraph capability registry (`capabilities/CAP-*.yaml`) as of this date.

## What's actually new (2025 → 2026)

The frontier moved from *"how do I chain LLM calls"* to *"how do I manage the
context that flows through the chain."*

1. **Definitional convergence.** "Agent = an LLM autonomously using tools in a
   loop." Everything else (prompt chaining, routing, parallelization,
   orchestrator-workers, evaluator-optimizer) is now framed as *workflows* —
   predefined code paths. The standing guidance is **"start simple; add agency
   only when it demonstrably helps."** This directly endorses YAMLGraph's thesis:
   most value lives in declarative workflows, not autonomous agents.

2. **Context engineering is the new discipline** (the biggest shift). Because of
   *context rot* — recall degrades as tokens grow (n² attention, every model) —
   context is now treated as a finite, depleting budget. Three concrete techniques
   have crystallized:
   - **Compaction** — summarize-and-reinitialize when nearing the window limit;
     tool-result clearing is the lightest form.
   - **Structured note-taking / agentic memory** — the agent writes notes to a
     file *outside* the window and reads them back (now a platform primitive).
   - **Just-in-time retrieval** — carry lightweight identifiers (paths, queries,
     links) and load data on demand via tools, instead of pre-stuffing context.

3. **Sub-agent architectures** — a lead agent coordinates; sub-agents each burn
   tens of thousands of tokens in *isolated* windows but return 1–2k-token
   distilled summaries. Separation of concerns at the *context* level.

4. **Protocol standardization** — MCP (tools), A2A (agent-to-agent), and the
   emerging AG-UI (agent↔user streaming) are becoming the interop substrate.

5. **Anti-framework caution** — the recurring warning: frameworks that *obscure
   the underlying prompts and responses* are a liability. Keep prompts inspectable.

## Where YAMLGraph already stands

The registry is surprisingly current. Already covered:

| Trend | YAMLGraph capability |
|---|---|
| Workflows-first | the entire YAML-graph model |
| Routing / parallelization / voting | `router`, `map`, `race`, parallel fan-out edges |
| Tool protocol (MCP) | `mcp-server-interface`, `per-graph-typed-mcp-tools` |
| Agent-to-agent (A2A) | `a2a-call-node`, `a2a-server`, consumer phase 2 |
| Sub-agent delegation | `copilot-node`, `shared-graph-invocation`, `subgraph-map` |
| Evaluator-optimizer | `verification-gate-pattern`, reflexion demo |
| Prompt visibility (anti-framework) | YAML prompts are the artifact — already inspectable |
| Prompt caching, thinking budget, streaming | all present |

YAMLGraph's "config-as-truth, prompts-as-files" design is *itself* the antidote to
the anti-framework warning — prompts are never hidden behind code.

## The real gaps — what matters from YAMLGraph's perspective

The whole **context-engineering layer is absent.** YAMLGraph has *state
persistence* (checkpointing) but no notion of **context as a managed, finite
resource**. The state TypedDict grows monotonically; nothing compacts it, and no
node curates what the next LLM call actually sees.

High-value missing primitives, in leverage order:

1. **Compaction node** *(highest impact, smallest spec)* — summarize-and-reset
   accumulated state / message history when a token threshold is crossed. The
   single most impactful addition for any long-running graph; the chaplain and
   dungeon-master examples already hit this wall.

2. **Memory primitive (structured note-taking)** — a first-class `memory` node or
   tool that reads/writes durable notes *outside* graph state, pulled back in
   just-in-time. We already *use* this pattern in our own `/memories/` tooling;
   YAMLGraph has no declarative equivalent.

3. **Lazy / reference variables for just-in-time context** — today
   `variables: "{state.x}"` eagerly inlines full payloads into every prompt. A
   lazy/reference variable (pass a path or query, let a tool fetch on demand)
   would directly cut context bloat.

4. **True orchestrator-workers node** *(defer)* — `map` requires a *predefined*
   list; the 2025 pattern is **dynamic decomposition** where the orchestrator
   decides the number and nature of subtasks at runtime, then synthesizes.
   `copilot` delegates but doesn't decompose-and-synthesize as a graph primitive.

5. **Context-budget observability** — we trace tokens (`--token-usage`,
   LangSmith) but don't treat *context rot / window pressure* as an operational
   SLO. Per Commandment 9, this is an un-instrumented production-defect class.

## Recommendation

Maximize leverage with minimal new surface:

1. **Compaction node** — highest impact, smallest spec; existing long-horizon
   graphs need it now.
2. **Memory / note-taking primitive** — unlocks long-horizon coherence across runs.
3. **Lazy / reference variables** — just-in-time context.
4. **Defer** the dynamic orchestrator-workers node until a concrete graph demands
   it (Scripture: "add agency only when it demonstrably helps").

## Red-Hat caution

Chasing every agentic trend risks the exact abstraction-bloat Anthropic warns
against. YAMLGraph's edge is *declarative, inspectable, validated*. Compaction and
memory fit that mold (config + a Pydantic-typed node), but a fully autonomous
orchestrator-worker loop pushes toward the opaque-framework failure mode. Keep
every addition declarative.

**Seed:** If context is a finite budget, should a YAMLGraph graph be able to
*declare* its context policy (max tokens per node, compaction trigger, which state
keys are ephemeral vs. durable) the same way it declares state keys today — making
context management a first-class, validated property of the graph rather than an
imperative afterthought?
