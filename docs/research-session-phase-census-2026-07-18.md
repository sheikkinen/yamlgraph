# Research: Session Phase Census — where an interactive enforcement session actually spends its tool calls

**Date:** 2026-07-18
**Method:** instrumented self-census of one interactive agent session
(id `a904c468`, 2026-07-14 → 2026-07-18, 82 user turns), joining the
Copilot session store (`turns` table) with the raw session transcript
(5,032 JSONL events, 923 tool calls). Raw extraction script output:
`tmp/session-phase-census.txt` (ephemeral); the categorization regexes
are reproduced in Appendix A so the census is re-runnable on any
transcript.
**Question:** which phases of the plan→judge→enforce doctrine consume
the session, and which of them could be delegated off the expensive
interactive agent?

## 1. The session under the microscope

One multi-day interactive session that executed seven full doctrine
cycles (FR-739, 740, 741, 742, 743, 744, and the 745/746/747 arc),
plus the introspection work that produced the Scripture interrogative
canon and the VS Code data-model map. This is a *representative*
heavy session: terse human commands ("judge 744", "enforce", "diary"),
agent executing complete measure→judge→RED→GREEN→record→commit→push
arcs under pre-commit enforcement, with 3+ parallel sessions sharing
the repo.

## 2. Phase taxonomy from the turn log

The 82 user turns cluster into seven phases:

| Phase | Turns | Example commands | Delegable? |
|---|---|---|---|
| Research / introspection | ~20 | "check all hooks — are there still more", "datamodel of the vscode storage", "introspection, philosophical level" | No — this is the paired-discovery lane |
| Plan (FR drafting) | 4 | "create frs", "draft frs" | Partially (template + triage graph already mechanize the checklist tier) |
| Judge | 5 | "judge 739", "judge 744" | No — 6-for-6 judgements changed designs *by measurement*; an agent that cannot be surprised cannot judge (diary: the-judge-that-shouldnt-be-a-hook) |
| Enforce (RED/GREEN authorship) | 9 | "enforce 740", "reread and enforce 746, 745, 747" | No — the code is the work |
| Reflect / diary | 9 | "diary", "repo memory --> diary" | No — the Distill rite is the knowledge capture |
| Demo / verification runs | 2 | "run the tools / demo" | Already cheap |
| **Mechanical tail** | woven into every enforce | (never commanded — implied by "enforce") | **Yes — see §4** |
| Retries ("Try Again") | 13 | context/length stalls | Symptom, not phase |

The mechanical tail is invisible in the turn log — no human turn ever
requests it — but dominates the tool-call log. That asymmetry is the
finding.

## 3. Tool-call census

923 tool calls; 535 were terminal commands. Categorized by regex over
the actual command strings (Appendix A):

| Category | Count | Share of terminal cmds |
|---|---|---|
| read/inspect (grep/sed/cat/ls...) | 210 | 39% |
| **git dance** (add/commit/push/status/diff/reset/log) | **201** | **38%** |
| pytest runs | 58 | 11% |
| other | 28 | 5% |
| lint dry-run (ruff/radon) | 14 | 3% |
| cap/req bookkeeping | 13 | 2% |
| **product execution** (`yamlgraph graph run/lint`) | **8** | **1.5%** |
| board/changelog regen | 3 | <1% |

Two corrections make the picture starker:

1. A large fraction of "read/inspect" is *reading hook bounce logs
   and commit-cycle output* — functionally part of the git dance.
   The true mechanical share is well above 40%.
2. The 8 product-execution commands include the FR-745 acceptance
   runs. **The framework this repository exists to build was executed
   8 times in a session that ran git 201 times.**

### The bounce anatomy

Every GREEN commit paid the same fixed choreography, observed ~10
times in this session with zero variation in the recovery move:

```
ruff format (dry) → git add <explicit list> → git commit -F tmp/msg.txt
  → BOUNCE "files were modified by this hook" (ruff-format)
  → git add <same list> → retry
  → BOUNCE (end-of-file-fixer on confessions.md)
  → git add <same list> → retry → pass → git pull --ff-only → git push
```

FR-745's commit took 3 attempts; FR-747's RED took 2. Each attempt
costs a full hook cycle (~3 min pytest). The recovery action is
deterministic: *re-add the identical file list and retry*. No
judgement is exercised anywhere in the loop — the only LLM-authored
inputs are the commit message and the file list, both fixed before
the first attempt.

### Secondary mechanical sinks

- **CONF line-number rot:** `# noqa` confessions are keyed by line
  number; edits above the line invalidate them. Two bounced commits
  in this arc alone. Re-keying is mechanical.
- **CAP/REQ scaffolding:** new-capability commits require a CAP yaml,
  a REQ id, an ARCHITECTURE.md row (regenerated by hook — re-add
  after failure), and pytest marks. 13 commands + the known
  **cap-req-id-allocation race** across parallel sessions (repo
  memory: two sessions allocating the same next-free id).
- **Parallel-session index hygiene:** the staged-check before every
  commit is doctrine (`one_session_one_repo`); this session caught a
  foreign staged FR-748 exactly once, and the cure was one
  `git reset -- <file>`. The check is cheap; the *choreography around
  it* (stash cycles, pull dances) is where sessions historically
  burned time. The human vetoed it live: "that's the git dance —
  just commit and push."

## 4. Could the dance be delegated?

### To a deterministic script — yes, and precedent exists

The chaplain's autonomous lane already automates precisely this tail:
`scripts/finalize_merge.sh` creates the changelog fragment, updates FR
status, stubs the diary, stages, and commits — for the watcher
pipeline. The interactive lane redoes all of it by hand, every arc.
The delegation target is therefore not new machinery but **parity**:

**Proposed: `scripts/enforce_finalize.sh <FR-id> <msg-file> <file...>`**
1. Pre-commit dry-run on the touched files (`ruff format`, `radon cc
   -n D`, `wc -l` vs the 450 cap) — the graduated pre-commit-dry-run
   heuristic, mechanized.
2. Staged-index check (empty or same-FR only) — the
   `one_session_one_repo` ritual as a gate, not a choreography.
3. `git add <explicit list>` → `commit -F` → on "files were modified
   by this hook": re-add the same list, retry (bounded, 3×).
4. `git pull --ff-only && git push`.
5. Constraint: **`automation_inherits_doctrine`** — the script retries
   *through* hooks; it never sets SKIP, never `--no-verify`.

**Also mechanizable, separately:**
- CAP/REQ scaffolder: allocate next-free ids *at stage time* from the
  registry (closing the allocation race), emit CAP yaml from template,
  print the pytest-mark line.
- CONF re-keyer: recompute `#LNN` anchors in `docs/confessions.md`
  from the current file content.
- Both are LLM-free; the linter-must-stay-llm-free rule applies to
  these for the same reason (repo memory).

### To a subagent — no, for git; maybe, for scaffolding

A subagent holding git adds a **second actor to the shared index**,
multiplying the exact hazard `one_session_one_repo` records three
strikes for (staged files swept into foreign commits; the FR-748
collision was the live witness *during this census*). The dance's
only judgement content — the commit message, the file list — is
already in the enforcing agent's context; a subagent would need it
handed over anyway. Script beats subagent wherever the recovery
policy is a fixed loop.

Analysis/census tasks (like this document's extraction) are good
subagent material: read-only, self-contained brief, single artifact.

### To a chaplain graph — wrong tier

The tail has zero LLM judgement; a graph would put a model in a loop
a shell conditional closes. Same reasoning that made the FR-745 hook
reminder-only (F1: no hook-time LLM) applies at commit time.

## 5. What must stay on the expensive agent

The phases that produced this week's value are exactly the
non-delegable ones: judgement-by-measurement (6-for-6 design changes),
RED/GREEN authorship, and the diary. The economics mirror FR-744's
delegation finding ($0.03 graph vs $4 inline) and FR-745's two-tier
split: route each tier to its cheapest sufficient substrate, and
never let the cheap tier sign. The git dance is the cheapest tier of
all — it wants a shell script, not a model.

**Projected effect:** collapsing the tail to one command removes
~200 terminal calls and most hook-cycle minutes from a session like
this one — roughly a third of tool traffic — while *increasing*
doctrine compliance (the dry-run and staged-check become unskippable
preconditions instead of remembered rituals).

## 6. Disposition

This document is research (Commandment 1). The actionable follow-up
is one FR: `enforce_finalize.sh` + CAP/REQ scaffolder + CONF re-keyer,
judged against the census numbers above. First consumer: the next
interactive enforce arc; first event: its first GREEN commit.

## 7. Correction (same day): the script verdict is falsified by its own evidence

§4's "the recovery action is deterministic" described only the
sunshine path (clean worktree, formatting-only bounces). The session's
own hook log refutes it. Hooks that actually fired across this one
arc's commits:

```
2× ruff-format          → re-add same list          (scriptable)
1× end-of-file-fixer    → re-add same list          (scriptable)
2× req-coverage-strict  → NEW CAP yaml + REQ id + ARCHITECTURE row + pytest mark
1× hedging-check        → REWORD prose (FB001 token)
1× prior-art-gate       → WRITE a disposition line
1× (environment)        → pre-commit not found: dead venv
1× (staging)            → target path gitignored
1× (index)              → foreign staged FR from a parallel session
```

Five of nine failure classes are not "re-add and retry" — they demand
*producing new artifacts* (CAP/REQ/fragment), *editing prose*
(hedging, CONF anchors), *changing commit metadata* (a scope shift
mid-fix flips feat→fix, which flips the changelog requirement), or
*repairing the environment*. The cascade is real: ruff moves lines →
noqa anchors rot → the fix commit changes type → changelog demanded →
new REQ → ARCHITECTURE regenerated by a hook → a file **outside the
original list** must be staged. A bounded re-add loop deadlocks or —
worse — force-feeds the wrong remedy. The end result is
**coordination**, not repetition.

### Corrected verdict: split scriptable parts from coordination; give coordination a small-model agent

The delegation target is a **chaplain-style yamlgraph agent** (the
tested pattern: agent node, small model, prepared instructions, tool
loop with limits):

- **Tier 0 — scripts as tools** (LLM-free, each a pure function):
  staged-index check, ruff/radon dry-run, attempt-commit (returns
  hook output *classified*), CONF re-keyer, changelog-fragment writer
  (from material the master provides), board regen, CAP/REQ allocator
  (stage-time id allocation, closing the race).
- **Tier 1 — coordinator** (haiku-class agent node): runs the
  attempt→classify→remedy loop. Its instruction set is exactly §4's
  remedy catalog plus this section's failure classes — tested,
  version-controlled, judged like any prompt (the prompt-as-
  subagent-contract discipline: one judgement, closed inputs, bounded
  "do X, NOT Y"). It never edits code semantics, never rewords
  test/prose meaning, never SKIPs, never signs scope changes.
- **Tier 2 — escalation to the master agent**: any hook demand
  outside the catalog (unknown hook id, scope-changing remedy,
  type flip, prose rewording) returns a structured escalation —
  hook output + remedies attempted + proposed action — instead of a
  workaround. Commandment 6 as control flow: when the filter yields
  nothing, raise; never substitute. The master (fable-class) decides
  and either resumes the coordinator or takes over.

This is the FR-744/745 economics with its missing third tier made
explicit: **script < small-model coordinator < master agent**, each
escalating upward exactly when its competence ends, and only the top
tier ever signing. The chaplain's watcher-enforce lane is the
architectural precedent (graph-orchestrated enforcement with the
expensive judgement kept elsewhere); the census's bounce anatomy
becomes the coordinator's training document rather than a script's
control flow.

**Disposition (supersedes §6):** one FR — `enforce_finalize` chaplain
graph (coordinator agent + Tier-0 tool scripts + escalation
contract). First consumer: the next interactive enforce arc; first
event: its first GREEN commit; kill criterion candidate: if >50% of
invocations escalate, the catalog is wrong and the tier collapses
back into the master agent.
