# FR-1163: The test that expected the rows I imagined

**Date:** 2026-11-14
**FR:** FR-1163 (a failed strict map keeps its evidence and its cost)

## What happened

The RED tests expected the collected rows to be `{"v": "a"}` and
`{"v": "c"}`, the worker's own output. GREEN produced
`{"_map_index": 0, "v": "a"}`. The snapshot was right and the test was
wrong: the collect channel always stores rows with their branch index, on
success too. I had written the expected value from the worker function, not
from the channel the user actually receives.

The same pattern appeared in the plan. It assumed LangGraph might wrap the
join's exception and reserved a `__cause__` branch for that. The first real
`invoke` / `ainvoke` showed the exception reaches the caller unchanged. Both
corrections came from running the real compiled graph, and neither came from
reading the code more carefully.

A third case: AC-09 required "byte-identical success output". A substring
assertion cannot prove that. A scratch script ran the same five success cases
against main and the branch and diffed the bytes; only then was a golden
string worth pinning.

## Trap: expectation_from_the_producer

When a test asserts what a boundary delivers, writing the expected value from
the producer's code skips the layers in between (reducers, wrappers, index
tags). The test then condemns a correct implementation.

## Heuristic

For a boundary assertion, take the expected value from one real run through
the boundary on the old code (the raw record), not from the function that
feeds it. "Unchanged" claims need a cross-checkout byte diff before a golden
is written.

**Seed:** Should RED tests for snapshot-style fields be generated by
capturing one run on the pre-change commit, so an expectation can never be
written from imagination? A small `capture_on(commit, scenario)` helper
would turn the snapshot script used here into a reusable witness.
