# 2026-07-01 FR-630/631/632: Three Boundary Fixes — The MagicMock Trap

## Context
Enforced three framework defects surfaced by the FR-628 wiki-memory demo:
- FR-630: `loop_exits: END` linter/runtime disagreement (2-line fix)
- FR-631: Variable string interpolation `wiki/{state.X}.yaml` (regex branch)
- FR-632: Pydantic models breaking Jinja2 tojson (boundary normalization)

## Trap: MagicMock Duck-Typing

**Trap:** `hasattr(mock, "model_dump")` is always True on MagicMock. So is
`hasattr(mock, "model_fields")`. The naive Pydantic detection broke ALL
tests using MagicMock as LLM return values.

**First attempt:** `hasattr(result, "model_dump") and hasattr(result, "model_fields")`
— still True for MagicMock.

**Fix:** `hasattr(type(result), "model_fields")` — checks the CLASS, not instance.
`type(MagicMock())` is `MagicMock` class which doesn't auto-generate attributes.
Real Pydantic models define `model_fields` on the class via metaclass.

**Bonus:** This also avoids the Pydantic V2.11 deprecation warning about
accessing `model_fields` on instances.

## Trap: Breaking Change Cascade

**Trap:** FR-632 is a semantic change (state stores dict instead of model).
Existing tests assert `result["key"] == pydantic_instance`. Need to update
ALL such assertions to `== instance.model_dump()`.

**Heuristic:** When a boundary normalization changes what downstream consumers
receive, grep for assertions comparing against the OLD type. The test updates
ARE the acceptance criteria for the breaking change.

## Heuristic
**Duck-typing detection for Pydantic:** Always check `type(obj)` not `obj`
when distinguishing real Pydantic models from mocks. MagicMock defeats any
instance-level `hasattr` check.

## Seed
Should the framework enforce a policy that state values are always
JSON-serializable? A compile-time or test-time check that no BaseModel
survives past a node boundary would catch this class of bugs automatically.
