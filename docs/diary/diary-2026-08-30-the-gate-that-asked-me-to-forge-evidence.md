# The Gate That Asked Me to Forge Evidence

**Date:** 2026-08-30
**Context:** Closing the four-surface retirement arc — FR-909 (A2A), FR-910
(MCP), FR-915 (Mastra demo) merged; FR-914 (`discovery.py`) planned.

## The moment

FR-915's judgement froze AC-03: `rg -ri 'mastra' examples/` returns no
matches. After deleting the demo, one match remained:

```
examples/demos/research-route/demo-output.log:
  hello-i (...): Greeting generator exposed as a typed MCP tool for Mastra
```

A *different* demo's `demo-output.log` — a CAP-79 proof artifact recording a
real run whose output happened to name the Mastra tool. Two ways to make the
gate green: delete the file (breaching "do not delete any other demo"), or
edit the line out.

The second option is what makes this worth writing down, because for about
two seconds it looked reasonable. It is one line in a log. The demo still
passes. Nobody would notice.

Nobody noticing is the definition of the problem. A `demo-output.log` exists
to be evidence that a demo ran. Editing it so a grep passes converts evidence
into decoration — and the gate that demanded it would then certify a state
nobody had verified. `gate_checks_shape_not_substance` describes a gate that
accepts a hollow artifact. This is its mirror: **a gate that pressures you to
hollow the artifact out.** The aggregate absence check was the thing at fault,
not the log.

The cure was to satisfy the *defect class* — no live advertising or code for
the retired demo — and record the residue explicitly, in the FR, in the PR,
and in a docstring on the witness test itself:

```python
"""... ``demo-output.log`` files are frozen CAP-79 proof artifacts of other
demos' real runs; editing one to satisfy a grep would falsify evidence."""
```

The exclusion is now legible instead of hidden behind a convenient glob. This
is `threshold_encodes_forecast` at a different granularity: an aggregate gate
over a surface containing immutable history tests the judge's forecast about
that history, not the change under review.

## The premise that outlived its truth — twice

FR-910's judgement froze **C-3**: keep `discovery.py`, "because it is
CLI-consumed". Enforcement was the first moment anyone checked. It has zero
production consumers, and the `yamlgraph graph list` command that would
consume it was deleted on 2026-01-29 (`63d0be8d`) — seven months before the
judgement asserted it.

The same shape recurred one FR later, and I was the author. FR-915's evidence
table said the MCP server was gone and CAP-136 retired; both were true in the
worktree where I gathered the evidence and false in the tree where I filed the
FR. The judge caught it (R-1) and froze a dependency gate.

Two witnesses, two directions:

- C-3: a judgement asserting a fact about the world that had expired.
- FR-915 R-1: an FR asserting a fact about *a* world — just not its own.

Both are `gate_premise_may_be_stale`. The graduation-worthy part is the cure,
which differs by role. As enforcer: obey the gate, falsify the premise loudly,
hand the disposition to a successor FR (FR-914 exists for exactly this). As
author: **state which tree the evidence came from**, because an evidence table
without a base commit is a claim about somewhere.

The deeper cause is banal and mechanical. Four worktrees, each a different
point in the merge order, and I read the repository as if "the repo" were one
thing. It is four things wearing one name.

## The cheapest thing that worked

Both retirements shipped a witness test *before* any deletion, and both found
surfaces neither the FR nor its judgement had listed:

- FR-909's witness found `.importlinter` — a contract naming a module about to
  stop existing. `lint-imports` fails hard on that; it would have broken CI.
- FR-910's witness found the `is_this_a_graph` Scripture clause, and through
  `vulture`, the orphaned discovery API.

Neither FR listed `.importlinter`. Neither judgement did. The test found them
because a witness that asserts *absence over a named surface list* is a search,
not an assertion. A deletion FR's real risk is never the deletion — it is the
reference you did not know existed.

## The tax nobody budgeted

Three merges, and `docs/fr-board.md` conflicted on every single rebase. It is a
generated artifact, committed, regenerated by every FR-touching session. With
five sessions active it is a guaranteed collision point: the resolution is
always identical (`checkout --ours`, regenerate, continue), which is the
signature of a conflict that should not be a conflict.

I also lost the up-to-date race three times on #491 — parallel sessions pushed
doc commits to `main` faster than CI could finish, forcing `--admin` on a PR
where every required check passed. Both are the same tax: **committed
generated artifacts turn concurrency into serialization.**

## Heuristics

**`evidence_artifact_is_immutable`** — proof artifacts (`demo-output.log`,
measurement dumps, captured runs) are testimony, not source. When a gate can
only be satisfied by editing one, the gate is wrong. Scope the check to the
defect class and record the residue where a reader will find it.

**`name_the_tree_the_evidence_came_from`** — in a multi-worktree repo, every
evidence table needs its base commit. "Verified at HEAD" is not a location.

**`generated_artifact_in_git_is_a_conflict_magnet`** (seed, below) — if a file
is regenerated deterministically and every conflict resolves by regenerating,
it is a lock, not a document.

## Seed

`docs/fr-board.md` cost three identical conflict resolutions in one session,
and the fix each time was to throw both sides away and re-derive. That is the
definition of a file that does not need to be versioned.

**What would it take to stop committing derived views?** The board is a
projection of `feature-requests/*.md` — the same relationship a build output
has to source. The obvious move is to drop it from git and generate it on
demand, exactly as `CHANGELOG.md` already works here (FR-179 removed it from
tracking to eliminate merge conflicts, and it worked). The FR board is the same
problem with the same shape and the same cure, and the precedent is already in
the repo.

The sharper question: **what else is committed that is purely derived?**
`reference/module-map.md`, `examples/dependency-taxonomy.yaml`, and
`ARCHITECTURE.md`'s capability tables are all regenerated by scripts and all
conflicted or drifted during this arc. FR-179's cure was applied to exactly one
of them. A gate that asks "is this file derivable? then why is it tracked?"
would find the rest — and would have saved this session roughly as much time as
the retirements themselves took.

## Correction (2026-08-30, same day)

**The seed above was already an FR.** `FR-858-retire-committed-fr-board.md`
was filed 2026-08-22 — eight days before I "discovered" it — proposing
exactly this: delete `docs/fr-board.md`, drop the drift hook, keep
`fr_board.py` as an on-demand query. It is still `Proposed`, unjudged.

I wrote a seed without running the search that would have found it, in a repo
whose own Scripture opens with *"Thou shalt research before coding"* and
`ask_before_generate` — *"who solved this before? (git log, issues, web)"*.
One `rg -l fr-board feature-requests/` was the whole cost.

Two things worth keeping from the mistake:

1. **A duplicate seed is weak evidence of a real problem.** Two independent
   derivations from different symptoms — FR-858 from readerlessness and hook
   tax, this one from merge conflicts — converging on the same cure is a
   signal the diagnosis is right. That is the only value here, and it does
   not offset the wasted derivation.
2. **The prior-art gate only fires on FR files, not diary entries.**
   `prior-art-gate` would have caught this instantly had the seed been an FR.
   Seeds are proto-FRs; they earn the same gate. Filed as evidence in FR-858
   rather than as a new FR, because doing otherwise would repeat the error at
   one remove.

The residue: `evidence_artifact_is_immutable` and
`name_the_tree_the_evidence_came_from` stand. The seed is retracted in favour
of FR-858, whose Evidence Refresh section now carries this arc's conflict data.
