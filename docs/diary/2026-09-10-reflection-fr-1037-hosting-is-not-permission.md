# Hosting capability is not hosting permission

The small-batch hosting discussion began with a working reference: deviant-daily
already runs scheduled and manually triggered jobs in GitHub Actions. Reading
its workflow answered how execution works, but not whether an unspecified new
application belongs on the platform. Official GitHub terms added the missing
boundary: low volume, personal use, and free compute do not establish eligibility.

**Trap:** working_system_inertia combined with an unverified provider premise.
A functioning example can turn into an architectural permission slip if the
reference is treated as evidence for more than it demonstrates. Likewise, a
webpage link to an authenticated workflow form is not a custom browser dispatch.

**Heuristic:** separate three questions before proposing infrastructure: can the
platform do it, may this workload use it, and does the user need the additional
interface? Reading the actual reference, reading provider terms, and asking the
operator produced three different answers. The operator accepted the native form,
removing the immediate need for a credential-bearing trigger service.

The durable plan preserves the open eligibility gate rather than implying that
merging prose deploys or approves an application. No provider execution was needed
to document the distinction.

**Seed:** Can a hosting-plan template require separate witnesses for capability,
permitted use, and first-user interaction before any infrastructure is proposed?
