# Reflection — FR-1094: the lock was the test

**Date:** 2026-09-26
**FR:** [FR-1094](../../feature-requests/FR-1094-tests-never-write-into-repo-tree.md)

## What happened

One unit test wrote an untracked probe into the real `feature-requests/`.
On a writable CI checkout that was invisible; on the FR-889-locked main
checkout it was the only red test in 6,904. The fix was a `root` parameter
and a temporary git repo. The guard against the next one was one CI step:
run the suite under the same `lock-main` the main checkout already uses.

## Trap

**Environment asymmetry hides a boundary.** CI was the one place that ran
every test, and also the one place where governed roots were writable. The
lock existed and was proven; it was just never applied where tests run. An
audit hook (the preserved dissent) would have been a second copy of the
same boundary, and the copy would have drifted from FR-889's root list.

## Heuristic

When a local invariant is enforced by the environment, make CI run in the
same environment before writing a new detector. Reusing the mechanism
cannot drift from it; a detector can.

A smaller one from the run itself: the first locked run carried two extra
flags (`PYTHONPATH`, `-p no:cacheprovider`) out of caution. The AC named
an exact command. The rerun with the exact command was the evidence; the
cautious run was not.

## Seed:

Which other FR-889-style environment invariants (hook state, lane
markers, venv boundaries) differ between CI and the main checkout, and
could each be closed by running CI under the same setup verb instead of
adding a check?
