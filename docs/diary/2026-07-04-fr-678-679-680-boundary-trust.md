# Diary — FR-678/679/680: Trusting the Boundary Enough to Let It Crash

**Date:** 2026-07-04
**FRs:** FR-678 (narrow catch), FR-679 (consolidate retry/fallback), FR-680 (provider registry)

## What happened

Three post-FR-676 hygiene FRs, enforced in sequence. All three orbit the same
star: the LLM-provider boundary, and how much we trust it.

- **FR-678** narrowed `except Exception` around a Pydantic `model_validate` to
  `except ValidationError`. A schema mismatch is a legitimate fallback trigger;
  a `TypeError` is a defect wearing the fallback's clothes. The broad catch
  turned every programming bug into an expensive, silent LLM re-invoke.
- **FR-679** deleted the duplicate fallback block that FR-676 *created* while
  achieving sync/async parity by copy-paste. One `attempt_structured_invoke`
  in `executor_base`, two callers keeping only their own sleep primitive.
- **FR-680** turned an 11-branch dispatch into a registry dict and, more
  importantly, gave keyless tests to four provider branches
  (inception/replicate/xai/lmstudio) that had **never executed under pytest**
  because they skip without API keys.

## The trap I stepped in

FR-679's spec asserted `_build_schema_hint` was a "zero-caller wrapper — delete
it." I deleted it. `lint-imports` passed. Then a grep for the symbol found
`node_factory/race_node.py` importing it. The FR's premise was wrong, and I
had nearly shipped a broken import because the *judgement* said zero callers
and I was tempted to trust the judgement over the grep.

This is `partial_remediation` inverted: not "fix only the cited occurrence" but
"trust the cited absence." A spec claiming something does *not* exist is a
claim to verify, not a fact to inherit. The grep is cheaper than the assumption.

## The through-line

All three FRs are the same Scripture line: *"normalize at the boundary,
trusting no provider's type."* But there are two failure modes at a boundary,
and these FRs cover both:

1. **Over-trust** (FR-680): a silent Anthropic fallback for an unknown provider
   name — a plausible wrong answer instead of a loud `ValueError`.
2. **Over-defense** (FR-678): a catch so broad it swallows our *own* bugs while
   pretending to guard against the provider's.

The cure for both is the same: make the boundary *loud*. Raise on the unknown
provider. Let the `TypeError` propagate. The fallback fires only for the one
condition it was designed for (`response_format` rejection, `ValidationError`),
and everything else crashes where it should.

## Insight

FR-680's real value wasn't the registry — it was discovering that four dispatch
branches had zero test coverage because the *only* tests that touched them were
key-gated integration tests that always skip in CI. The refactor was the
*excuse*; the coverage was the *point*. Separating "which factory?" (cheap,
keyless) from "construct the client" (expensive, key-gated) is what made those
branches testable at all. Entanglement wasn't just ugly — it was hiding
untested code behind an API-key skip.

## Seed

If four provider branches never ran under pytest despite "passing" CI, what
other code is green only because the test that would exercise it is skipped for
lack of a credential? **Could a gate count skipped tests per module and flag any
production branch reachable only through an always-skipped test** — a
"coverage mirage" detector that treats a permanently-skipped test as zero
coverage, not as a pass?
