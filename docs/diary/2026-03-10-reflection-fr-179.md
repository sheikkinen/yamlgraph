## 2026-03-10: FR-179 — Implementation Reflection

**Context:** Replaced monolithic `CHANGELOG.md` (87 KB, 1427 lines) with per-FR fragment files under `changelog/unreleased/`, aggregated by `scripts/aggregate_changelog.py` on demand. The file was untracked via `git rm --cached` and added to `.gitignore`. Migration script split all existing entries into `changelog/{version}/` directories. Both enforcement gates (pre-commit `changelog-required` and CI `changelog-gate`) were updated to check for fragments instead of `CHANGELOG.md` modification. `finalize_merge.sh` now creates a YAML front-matter fragment instead of `sed`-editing a monolithic file.

**Trap:** `symptom_patch` — The original FR design included a "staleness guard" that would regenerate `CHANGELOG.md` on every PR to detect drift. This guard *itself* modified `CHANGELOG.md`, recreating the exact merge conflict it claimed to prevent. The mechanism was self-defeating: a prevention tool that touches the conflict surface *is* the conflict. This is also `downstream_fix` in disguise — the guard operated at merge time (callsite) rather than questioning whether a generated artifact belongs in version control at all (the boundary). The Judgement caught this: Option A (untrack entirely) eliminated the conflict surface rather than trying to police it.

**Heuristic:** A guard that modifies the artifact it guards creates the problem it claims to solve. When a prevention mechanism requires touching the conflict surface, eliminate the surface instead. The cheapest conflict is the one that cannot exist — untrack generated artifacts; generate on demand.

**Seed:** Which other tracked files in this repo are generated artifacts masquerading as source? The capability registry, aggregated docs, or CI-generated configs could harbor the same latent conflict pattern. Could a `make generate` target replace all tracked-generated-file anti-patterns with on-demand generation, the way `aggregate_changelog.py` replaced `CHANGELOG.md`?
